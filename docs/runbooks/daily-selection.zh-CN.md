## 前提

1. `docs/research/p6-registration.json` 已由 `scripts/research/registry.py` 的 `register()` 写出并**提交**，磁盘上的字节与 `HEAD` 相同。登记文件不存在或没有配置对象，第 1 步拒绝，退出码 2；登记文件自相矛盾（它的 `config_id` 与按它自己的 `config` 重新推出的不一致，例如写出后被改过），同样在第 1 步拒绝，退出码 3，与「运行的代码不是登记的代码」同一类：登记在，但不能作为登记的配置来运行。每日命令和前向报告共用这一处准入（`admit_registration`）。
2. 运行命令的检出，其受约束代码（`src/`、`scripts/research/`、`pyproject.toml`、`uv.lock`，以及 `scripts/daily_selection.py` 本身）与登记文件里的 `code_commit` 一致，工作区无未提交改动，`openalpha_cn` 从这个检出的 `src/` 导入；**运行的解释器与登记提交的 `.python-version` 同一个 `major.minor`**（从 `code_commit` 处读取，改工作区里的文件不算数），且**它装的第三方包与这个检出的 `uv.lock` 对这个解释器锁定的版本完全一致**（装了锁文件没有的包、或版本不同，都算不一致）。任何一条不满足，命令在第 1 步拒绝，退出码 3，并逐个点名不一致的包。

   `uv.lock` 是通用锁：同一个包可以按 fork 出现多次，每条带 `resolution-markers`。本仓库的锁就是这样：`numpy 2.4.6` 用于 Python 3.12 以前，`2.5.1` 用于 3.12 及以后。比对时只取标记对运行解释器成立的那一条。标记用标准库求值（`packaging` 只是测试依赖，这里没有新增运行时依赖）；读不懂的标记直接拒绝，不猜。依赖边上的 `marker` 不参与比对：它决定的是某个包装不装，不是装哪个版本，而锁里有、环境里没装的包本来就不算不一致。2026-09-28 实测：主检出共用的 `.venv` 是 Python 3.11.14、`numpy 2.4.6`，正是锁对 3.11 的答案，0 处差异。第 3 轮报告的"锁的是 `2.5.1`"是误判：当时的比对忽略了 `resolution-markers`，每个包名只取了最后一条。
3. **所以定时运行不在开发检出里跑，而在一个钉在登记提交上的专用 worktree 里跑**（见「定时」）。主检出里继续开发、提交，都不会再让某一个前向交易日因为代码变了而被拒绝、白白丢掉；手动运行时同样建议从这个 worktree 跑。
4. 运行目录的面板已回填到当年，因子在训练/滚动窗口内的历史时点已构建（滚动 IC 与 walk-forward 需要窗口内每天的截面；本命令只构建当天及此前错过的交易日，不回填历史，见「错过的交易日」）。
5. `.env` 里有 `TUSHARE_TOKEN`。命令本身从不读取它：`panel build` 在 `TushareProvider` 内部解析凭据，本命令只给传输层套了一个按 `api_name` 计数的外壳。

## 手动运行

在钉住的 worktree 里（路径以你的为准），用它自己的环境 `.venv`（`--pin-worktree` 建的）：

```bash
UV_PROJECT_ENVIRONMENT="$PWD/.venv" uv run --no-sync --env-file .env "$PWD/.venv/bin/python" scripts/daily_selection.py --runtime-dir ~/openalpha-research
```

不需要 `PYTHONPATH`：这个环境里的项目是指向本 worktree `src/` 的可编辑安装。`uv run` 只用来读 `--env-file`。

**`--env-file` 必须是不含空白的名字，在 worktree 里写相对的 `.env`。** uv 会按空格拆分 `--env-file`（`UV_ENV_FILE` 同样）：`--env-file "/x/env test/.env"` 报 `No environment file found at: test/.env`（2026-10-06，uv 0.9.29 实测）。主检出的路径含空格，所以不能把主检出的 `.env` 写成绝对路径传给它。`--pin-worktree` 在 worktree 里建一个 `.env` 符号链接指向主检出的 `.env`（见「定时」），在 worktree 里 `--env-file .env` 就读到它。

常用选项：

| 选项 | 作用 |
|---|---|
| `--registration PATH` | 登记文件，默认 `docs/research/p6-registration.json` |
| `--repo DIR` | 校验登记与代码绑定所用的 git 检出，默认脚本所在的检出 |
| `--as-of ISO` | 固定当天的时钟（默认现在）；该时刻已发布的最新交易日就是「当天」 |
| `--dataset T`（可重复） | 用这些面板目标代替按配置推导的目标（读行业的当天仍会加上行业目标） |
| `--full-update` | 更新当年全部目标（`FULL_UPDATE_TARGETS`），不管配置读什么 |
| `--max-staleness-days N` | 因子构建的新鲜度上限，默认 30 |
| `--top N` | 摘要打印前 N 名候选，默认持仓数 |
| `--json` | 以 JSON 打印当天结果 |
| `--pin-worktree DIR` | 在登记提交上创建或移动一个分离 HEAD 的 worktree，再用它自己的 `uv.lock` **离线**建它自己的环境 `DIR/.venv`（`uv sync --frozen --offline --no-python-downloads --all-extras --python <.python-version>`），建成后读回它的解释器版本，再在 `DIR/.env` 建指向主检出 `.env` 的符号链接（没有就只打印说明），打印提交号后退出 |

## 八步与失败时的行为

| 步 | 做什么 | 失败时 |
|---|---|---|
| 1 registration | 读登记文件；用 `registry.admit_registered_code` 校验提交状态与代码绑定；再核对运行解释器的 `major.minor` 与登记提交的 `.python-version`，并比对它已安装的包与检出的 `uv.lock` 对这个解释器锁定的版本 | 文件缺失或不可读：退出 2；代码不是登记的代码、或环境不是锁文件的环境：退出 3 |
| 2 panel update | 对最新已收盘交易日所在年份跑 `panel build --incremental`，同一个 `--as-of`，目标按「每天取什么」推导；三张报表按增量规则只重扫还可能变的月份（见「每天取什么」），1 月里另建上一年的三张报表以重扫上一年 12 月；`fina_indicator` 单独一次调用，覆盖报告期年份 Y−1（以及 3 月 31 日之后的 Y），**未扫到的报告期年份在库里的行原样带入**所写的公告年分区（见下）；当年还没有任何公告时记录为空分区；当天的结果窗口或其下一交易日跨入下一年时，再建下一年的 `trade_cal`（1 次请求） | 退出 1，并转述 `panel build` 自己的拒绝理由 |
| 3 panel doctor | `panel doctor` 与依赖门 `data-check`，数据集为本次更新写的数据集（不含按上市年份分区的 `stock_basic` 和行业目标），带上当天 `--session`，指数数据集带三个指数代码；当天是一年的第一个交易日时，上一年也一并检查（`return_paths` 要跨年比较前一交易日）。`fina_indicator` 单独检查一次，只查已存在的公告年（一年的头几天可能还没有任何公告） | 不 clean 就停，第 4–7 步都不执行 |
| 4 factor build | 配置读到的每个因子档位，在**当天及此前错过的交易日**的 16:30（上海）信号时点构建：从该档位库里最晚的信号时点之后到当天（含）的每个交易日（按库里的 `trade_cal`）；已有构建的时点跳过；档位在库里从未构建时只建当天。一个档位错过的交易日最多补 `MAX_CATCH_UP_SESSIONS` = 20 个（见「错过的交易日」） | 退出 1，转述构建拒绝；错过的交易日超过 20 个时拒绝、一行不写，错误里写出缺口范围和分批补建的 `openalpha factor build` 命令 |
| 5 candidates | `strategy_view.score_day`：回测自己的读路径与打分器给当天打分排序 | 退出 1 |
| 6 target weights | 回测自己的调仓规则 `strategy_backtest.target_holdings`，上一次日志里的目标持仓视为账面 | —— |
| 7 prediction | 当天打分登记进预测库，必须早于下一交易日 09:15（集合竞价开始，开盘价由它决定） | 已到或已过下一交易日 09:15（晚跑、补跑过去的日子）则拒绝登记，什么也不写 |
| 8 summary | 打印摘要并写当日日志 | —— |

任何一步失败——包括步骤里没有预料到的异常——标准错误输出里都写明「step N (名称) failed」和原因，并给出本次运行到停下时已发出的 Tushare 请求数（失败也花请求），之后的步骤不执行。

**与其他进程共用面板时（V2-P6-028）。** 面板目录可以同时被多个进程读写（例如本命令与研究重建、另一次 `factor build` 并行），由目录里 `catalog.duckdb.lock`、`catalog.duckdb.gate` 两个锁文件协调。两种情况下第 2 步或第 4 步会停下，**本命令的退出码是 1**，二者都不是数据问题，处理办法都是等对方结束后**原样重跑**：一是面板被其他进程占用超过等待上限（默认 600 秒），什么都没读也没写；二是本次写入读取用于合并的分区之后，另一个进程先提交了同一分区（例如两次增量建库、或同一因子的两次构建同时进行），本次写入整体放弃、一行不写，重跑会在对方写入的结果上重新合并。

（2026-10-14 更正，`V2-P7-008`：此前这里写的是「以退出码 6 停下」，不对。退出码 6（`catalog_busy`）是单独运行 `openalpha panel build`、`openalpha factor build`、`openalpha panel doctor` 时它们自己的退出码；本命令在进程内调用它们，把这两种情况转述为该步的拒绝，`DailyExit` 只有 0、1、2、3。标准错误里的样子：第 2 步是 `` step 2 (panel update) failed: `panel build` exited 6: … ``，第 3 步是 `` step 3 (panel doctor) failed: `panel doctor` is not clean (exit 6): … ``，第 4 步是 `step 4 (factor build) failed: an unexpected fault: PanelCatalogBusyError: …` 或 `… PanelWriteConflictError: …`。所以定时任务若想只对这两种情况自动重试，要看标准错误里的 `exited 6`、`(exit 6)`、`PanelCatalogBusyError`、`PanelWriteConflictError`，不能看退出码。幸存者形态同样如此，见「幸存者形态」。）

另外，第 4 步的一次因子构建现在是**整体写入**：raw、processed、neutralized 三档要么一起写成，要么一档也不写——以前较高一档被拒时，较低档位已经写入；现在较高一档被拒，较低档位同样没有写入，需要时用 `--tier raw` 或 `--tier processed` 单独重建较低档位。

## 输出怎么读

摘要依次给出：

- **session**：当天交易日与固定的 `as_of`。
- **candidate list**：候选榜 ID（`dsl_` 加 24 位十六进制，是当天榜单内容的摘要），以及前 N 名与各自的组合分。榜单截到缓冲带（`buffer_rank`，无缓冲带时为持仓数）。
- **target weights**：`rebalanced`、`not a rebalance day`（沿用上一次目标）或 `held`（打分源当天没有答案，沿用上一次目标），括号里写明原因（`scheduled`、`the first day: no book yet`、`catching up the rebalance scheduled on …`）；每只 `1 / holding_count`，其余为现金；`turnover` 是与上一次目标权重的单边换手。
- **prediction**：预测记录 ID（`prd_…`）、`standing`（应为 `forward`）与结果可知时刻。
- **factor catch-up**（第 4 步补建了错过的交易日时）：补建的交易日，逗号分隔；当日日志里是 `result.factors.caught_up`（没有补建时为空列表，这一行不打印）。
- **tushare requests**：本次运行实际发出的请求数，按接口分列。
- **industry sweep**（当天取了行业归属时）：`whole-market states`（4 次请求）；库里还没有行业归属时为 `the l1_code slices (62 requests): …`；全市场答案自检不通过时为 `FELL BACK to the l1_code slices (62 more requests): <原因>`。如果每个读行业的日子都出现 `FELL BACK`，说明每天多花约 62 次请求，需要查原因。

## `fina_indicator` 的公告年分区为什么要带入旧行

`fina_indicator` 按报告期取、按公告日期分区，一个公告年由至少两个报告期年份拼成：比如公告年 2025 里有 2025 年的三份中报/季报，也有 2024 年报（2025 年 4 月公告）。每天只扫报告期年份 Y−1（3 月 31 日之后再加 Y），如果把扫到的行整份写进公告年分区，2024 年报就会从 2025 分区里消失，面板的「分区行数不许变少」守卫会拒绝，第 2 步在一个回填过的真实库上就会每天失败；一年的第一个交易日，公告年 Y−1 也是同样的情况。

所以在 `--incremental` 下，每个被写的公告年分区里，报告期年份**不在**本次扫描范围内的已存行原样带入，重新按本次的 `as_of` 盖入库时刻；在扫描范围内的行用本次取到的替换。结果与同一 `as_of` 下对全部相关报告期年份做一次全量构建逐字节相同（测试比对了两者的分区内容哈希），且不多花任何请求。带入的是已存的行：本次未扫到的报告期年份如果在上游被更正，要等下一次扫到它的构建才会进库——不带入也一样。另一种办法「只写所有来源报告期都扫到了的公告年」行不通：迟到的年报会落在很多年之后（`001278.SZ` 的 2018 年报 2022-01-06 才公告），当年的公告年分区几乎总含有每天扫不到的报告期，于是永远写不进去。

调仓按登记配置的 `start` 起算，每 `rebalance_every_sessions` 个交易日一次，与回测一致。walk-forward 模型的重训日也从 `start` 起算，当天使用的是最近一个重训日训练的模型，与从 `start` 回测到当天时回测使用的模型相同。

## 为什么不是 `shortlist run` 和 `portfolio construct`

计划原文写的是这两条命令，但它们实现的不是登记的策略：

- `shortlist run` 按已存档位值的加权和排序；策略是对每个成分在「所有成分都有值的证券」上标准化（`zscore_sum` 或 `rank_sum`）后再求和。它拒绝中性化档，也表达不了滚动 IC 加权和 walk-forward 模型，且没有研究证据时会被研究比例门拒绝。
- `portfolio construct` 按名次分档给权重，单票上限 25%、总敞口 80%，没有缓冲带；策略持有 `holding_count` 只、等资金、排名在缓冲带内的持仓保留、可按行业限只数。

所以候选榜就是策略自己的排序，目标权重就是策略自己的调仓规则，两者都通过 `run_strategy_backtest` 使用的同一组函数得到。测试 `tests/unit/scripts/test_daily_selection.py` 对静态、滚动 IC、walk-forward 三种打分源分别证明：读取登记记录的回测与登记配置本身的回测逐期成交、持仓、收益完全相同。

## 登记的预测是什么

批次由 `src/openalpha_cn/strategy_registration.py` 的 `signal_day_batch` 生成，「当天已登记的记录」由同一模块的 `session_record` 查找，前向报告（`V2-P6-012`）引用同一份定义。

- **walk-forward 模型**：就是当天在用模型给当天截面打的那一批分（回测把它们作为打分行），重新盖上登记时刻。
- **静态权重、滚动 IC**：没有拟合的模型，登记的批次声明的是组合分本身：`family` 为 `strategy_static` 或 `strategy_trailing_ic`，`feature_version` 为登记配置的 `config_id`，`seed`、`code_commit` 取自登记文件，超参数写明组合方式与登记文件摘要。制品里的「测量字段」来自当天的输入而不是手填：`feature_ids` 是成分键，`parameters` 是当天使用的权重，`training_cutoff` 是当天读到的任一打分行或计入的 IC 最晚变为可知的时刻，`training_example_count` 是这些行和 IC 的个数。每只被排序的证券带组合分；只有部分成分有值的证券以 `ABSTAIN_INCOMPLETE_FEATURES` 弃权。

同一天、同一声明下已经登记过记录时：分数相同则复用，不再写；分数不同则拒绝（已登记的记录有效，不允许第二个答案）。

### 回测怎样读这些记录（`V2-P6-011` 第 9–12 轮）

**威胁模型（已定）**：这里所有的东西都是本机文件，包括预测库和它的 `recorded_at` 时钟、日志、输入来源、已存的核实结论。下面这些检查防的是诚实运行中的出错、程序缺陷、意外损坏和上游更正；它们防不住掌控这块磁盘的人蓄意篡改。要防这个，需要一个外部的只追加见证（例如每天提交到 git 的摘要账本），这里没有做。前向报告的输出里也写明这一点（`daily_selection.INTEGRITY`）。

命令在收盘后约 18:30 登记，晚于 16:30 的信号时点。回测怎么读一条记录，看它的登记时刻 `max(predicted_at, recorded_at)`（`strategy_view._prediction_rows`）：

- **在信号时点当时或之前登记**：那时还没有更晚的信息，按原来的规则读，用入库时刻作为打分行的时钟。
- **在信号时点之后登记**：批次的 `as_of`（它读取输入的时刻）只是写入方自己的声明；次日 09:15 之前登记的记录，可能带进了当晚的公告或盘前消息。所以先要求它在成交那个交易日 09:15 集合竞价开始之前登记（`strategy_view.REGISTRATION_CUTOFF`，第 7 步用的是同一个定义），再交给检查（`strategy_registration.RecordCheck`）按下面的顺序判断：
  1. **绑定登记**，否则拒绝：
     - 组合记录：声明必须与登记的配置一致（`feature_version` 是 `config_id`，超参数里有登记文件摘要，`code_commit` 和 seed 取自登记）。
     - walk-forward 记录的声明是模型自己的，里面没有登记；还必须有一份本登记的输入来源（见下）点名它的批次。所以别的写入方（例如 `model daily-run`）对同一模型、同一天的记录不算这个登记的，推导直接忽略它，不会因为一天两条记录而拒绝整本账。
  2. **按它自己的登记时刻重算**：请求以 `as_of = registered_at(记录)` 读库，用 `score_day` 从已存的因子构建把那天重新打一遍分（不发请求），再过同一个 `signal_day_batch`。时点、制品和每一个分数都相等，就是 `verified`。按写入方当时能看到的库来读，登记之后才存进来的东西不会进入比较。
     - **登记时刻已经读不了库时**（fix round 14）：`adj_factor`、`suspend_d` 的读取按整个年分区判断 `not_yet_knowable`（看分区里最新一行的 `max_available_time`，`V2-P4-079`/`086`/`094`）。库往后追加了几天，这一年对更早的任何 `as_of` 都整体拒读，于是滚动 IC 和 walk-forward 的每条旧记录都会被拒绝。现在的做法：登记时刻读不了，就改在「这一天的来源所读各分区都已可读的最早时刻」重算，即这些分区 `max_available_time` 的最大值，且不早于登记时刻（`strategy_registration.readable_instant`、`_score_when_readable`）。登记时刻读得了的记录，仍在登记时刻判断，不受影响。
     - 只有「分区还不可知」这一类拒读才会改到更晚的时刻（fix round 15）：读取器此时抛 `panel.catalog.PartitionNotYetKnowableError`（仍是 `PanelStorageError` 的子类），检查沿异常链找它。其他拒读（缺分区、数据矛盾、程序错误）在登记时刻就是结论，不再换时刻重试。fix round 16 起，按行可见的读取（例如 `upstream_defects`）在日期普查里「每个日期都只少不多」时也抛它：少的行都存着、只是时钟在 `as_of` 之后（收益路径决定带着确认它的那次构建的时钟），更晚读就能读到；有日期多出来说明普查与分区不符，任何时刻都读不了，照旧拒绝。
     - 这个更晚的时刻不会放行登记时刻不会放行的东西。记录的数字在登记时刻就定了，带不进之后才到的行。两个时刻之间到的东西分两类：
       - 不影响这一天打分的：之后交易日的行（计入的 IC 其标签在信号时点前已退出；walk-forward 的训练标签在隔离期截止前已退出，打分截面取信号时点可见的）；以及因子构建，每天取信号时点及以前最晚的那次构建（`strategy_view._chosen_build`），登记之后重跑的构建不会替换当天原来那次。
       - 影响打分的：原地取代的因子构建（替换的构建时刻相同，所以会被取用）、重述的行、日期较早但晚到的行、登记之后才记下的收益路径决定（`V2-P6-020`）。重算就不一致，记录就不会是 `verified`：输入来源能指出变化就记为 unverifiable（照样定价、标出），否则拒绝。
       - 所以更晚的时刻只在登记时刻本来也会核实通过的地方给出 `verified`；其余情况要么拒绝，要么是标出的 unverifiable 放行，绝不会是 `verified`。
     - 请求只有一个 `as_of`，按数据集分别给时刻要把参数一路传进各个读取器和模型平面，所以这里用单一的更晚时刻，靠上面的论证和输入来源分类保证不变弱。持久化结论（`verdicts`）和输入来源的比对都与重算时刻无关，不变。
     - 持仓日的推导（`witnessed_days`）按日志固定的时刻重算那一天，也走同一个规则：那个时刻读不了库，就在可读的最早时刻重算，否则那个持仓日会被当成没跑完，下一条记录被误算成补做调仓。
  3. **重算不一致时，看这一天读过的输入是否在登记后被更正**。在第 7 步登记之前，命令把这一天读的输入写成一份输入来源（`daily_selection_provenance/<摘要>.json`，按内容寻址、只写一次）。只算来源真正读的数据集（`strategy_view.input_datasets`，由来源推出，不是一张固定的大表）：
     - 静态组合：它各个成分的因子层数据和构建清单；滚动 IC 和 walk-forward：还要加上定价标签用的数据（`daily`、`adj_factor`、`suspend_d`，以及记录收益路径决定的 `upstream_defects`——今天是 `V2-P6-013` 的剔除，合并 `V2-P6-020` 后还有它的收益路径决定）。价格基础数据的更正因此解释不了静态组合的不一致。
     - 文件带版本号：现在写的是 `daily-selection-input-provenance/v2`，覆盖 fix round 16 的窗口。fix round 16 之前写的 `v1` 文件照样能读，按它自己的版本算摘要；核实时，`v1` 从未覆盖的分区（walk-forward 从重训日往回多出的年份、阶梯序列多读的前一年）不参与比对，所以格式变化绝不会让一条记录变成 unverifiable。
     - 对每个分区，记下内容哈希和它的行摘要。行摘要只取记录当天及以前、并且在那天信号时点已经可见的行（`available_time` 和 `revision_time` 都不晚于信号时点），不含每次增量都会重盖的 `ingested_time`。所以之后每天追加的行、以及日期虽早但晚到的行，都不算更正。
     - **重算读在登记时刻之后时**（fix round 15）：标签用的数据（`strategy_view.LABEL_INPUTS`）是按请求的 `as_of` 读的，不按信号时点。所以在登记时刻和重算时刻之间才可见、日期落在这一天回看窗口里的行，重算读得到，记录读不到，而信号时点的行摘要看不见它们。典型的是 `upstream_defects` 里的收益路径决定：它带着确认它的那次构建的时钟，登记之后才记下。这类变化也算更正，写作 `<数据集>:<年> (rows of the window recorded after filing)`（`stored_rows_digest` 的 `since` 给出窗口起点）。因子构建不在此列：登记之后的构建不会是某一天取用的那一次。
     - 窗口按这一天实际读到的范围算（fix round 16）：walk-forward 的一天用的是它之前最近一次重训的拟合，训练窗口在那次重训之前，所以窗口从重训日往回数（重训间隔 + 训练期 + 隔离期 + 期限），而不是从这一天往回数；各数据集读的年份（`_dataset_years`）覆盖整个跨度。`adj_factor`、`suspend_d` 是阶梯序列，读窗口里的某一天用的是那天仍在生效的行，所以除了日期落在窗口里的行，还取每只证券在窗口开始前最新的那一行（`stored_rows_digest(in_force=True)`），读取的年份也多往前一年。登记之后才到的、在窗口开始时生效的因子变动，因此算作更正。
     这些输入有一个在登记后被更正（被取代的因子构建、`adj_factor` 重述、`V2-P6-016` 撤回、重述的收盘价、登记后才记下的收益路径决定），记录就记为 `unverifiable_inputs_corrected_after_filing`：照样定价（它是按时、绑定、在只追加库里的记录，定价它才能让账面等于当时的推荐），并列进检查的 `unverifiable`，由报告标出并计数，不会悄悄放过。没有任何输入被更正而重算仍不一致，就拒绝。
- 输入来源为什么是一个单独的小文件，而不放进预测记录：`PredictionRecord` 是 `extra="forbid"` 的 `alpha-prediction-record/v1`，加一个字段就是契约变更（第 3 条硬规则）。这个文件用自己的摘要命名、只写一次，这与预测库的规则相同；它点名自己是为哪个批次写的，所以只绑定一条记录。
- 前向报告用 `scripts/daily_selection.py` 的 `forward_record_check(运行目录, 登记, as_of=…)` 得到这个检查，并把它作为 `backtest_strategy(verify_late=...)` 传给回测。不传检查时，信号时点之后登记的记录一律拒绝。

实测：

- 18:30 和次日 09:14 登记、分数如实的记录，回测结果与配置自己的回测逐期相同，三种来源都是。
- 重算用的时刻正是每条记录自己的登记时刻。
- 改动一个分数（+0.001）的记录被拒绝；另一个登记名下的记录被拒绝；09:15 登记的记录被拒绝；16:30 登记的记录仍按原规则读。
- 登记后被取代的因子构建：如实的记录仍然放行，列为 unverifiable，名单里写明被更正的因子数据集。
- 登记后重述一个 IC 窗口内的收盘价：滚动 IC 记录列为 unverifiable（名单写明 `daily:2026`），账面照样定价。
- 库追加两个交易日之后（fix round 14）：同一天的滚动 IC 和 walk-forward 分数，在只到当天的库上按登记时刻算，与在追加后的库上按可读时刻算，时点、制品和每个分数都相同；追加后的库里还有一次登记之后才跑的反向重跑构建，也没有被取用。这样登记的旧记录是 `verified`；若当天的构建在登记后被原地取代，记录列为 unverifiable，名单写明因子数据集；日志记下的持仓日仍推导为 `held`。
- fix round 15：因子构建只到当天、标签数据多到两天之后的库上，旧记录同样是 `verified`（可读时刻取的是标签数据的时刻）。当年 `upstream_defects` 分区在登记前已有一条决定、登记后又记下一条窗口内的收益路径决定时，重算不一致的记录列为 unverifiable，名单写明 `upstream_defects:2026 (rows of the window recorded after filing)`；没有这条新决定时，同一条记录被拒绝。
- fix round 16：两年语料上，2027-01-12 的滚动 IC 记录（窗口从 12 月初开始）在登记之后才发布一次 2026-11-30 的因子变动时，重算不一致的记录列为 unverifiable（`adj_factor:2026`），没有这次变动时被拒绝；重训间隔 25、这一天距重训日 23 个交易日的 walk-forward 记录，登记后记下的一条 2026-12-04 收益路径决定（在从这一天数的窗口之外、从重训日数的窗口之内）同样使它列为 unverifiable（`upstream_defects:2026`）。

**已存核实结论的信任边界**：`reports/record_verdicts/<记录>.<输入来源>.<分区摘要>.json` 只是一份缓存，不是证据。键是记录 id、输入来源摘要，以及核实时各个分区的内容哈希和行摘要。沿用一条结论之前，要先比对这些分区是否原样还在：先比内容哈希，内容哈希变了就重算行摘要。有任何一个变了，就重新核实。所以程序缺陷或上游更正会把记录送回核实。它和其他文件一样，能写这块磁盘的人也能写它（见上面的威胁模型）。

同一次登记（同一交易日、同一批次摘要）出现两份输入来源文件时，按名拒绝：两份里分不出哪一份是那次运行写的。

意外损坏在这个威胁模型之内：

- 读不出来的核实结论文件（截断、乱码、缺字段）当作没有缓存，重新核实这条记录，并在日志里写出文件名。
- 读不出来的输入来源文件，与摘要和文件名对不上的一样，按名拒绝。

**成本**：

- 输入来源在第 7 步登记之前写。在研究库的一个 APFS 克隆上（只读取；全市场，2019 年 `daily` 88.5 万行、`factor_obs_reversal_1d_v1` 91.5 万行）实测：
  - 静态组合（`reversal_1d` 原始层）读 2 个分区，约 10 秒；
  - 滚动 IC（两个因子，IC 窗口 60 + 期限 5）读 8 个分区（两个因子的数据和清单、`daily`、`adj_factor`、`suspend_d`、`upstream_defects`），约 30 秒；
  - 同一次核实里再算一天，因为每行的哈希已经缓存，只多约 0.5–1.5 秒。
  - 回看跨年（例如 1 月）时，读的年份多一倍，时间也约翻倍。
- 每条记录只核实一次。之后的报告只要该记录读过的分区都没变，就直接沿用已存结论。判断「没变」通常只比对内容哈希；只有被追加过的当年分区，才在一次报告里重新读一遍，之后每条记录都用缓存。
- 同一次报告里，walk-forward 的拟合按（重训日，读库时刻，模型声明）缓存。
- 所以一次报告的重算成本，大约等于「上次报告以来新登记的记录数 × 每条的重算成本」，再加上每个变动过的分区读一次（上面实测每个分区约 10 秒量级）；第一次报告则要核实开始以来的全部记录。
- 在策略测试语料（8 只证券）上，每条记录的重算：静态权重中位数 0.056 秒，walk-forward 中位数 0.54 秒。
- walk-forward 每条记录的读库时刻都是它自己的登记时刻，彼此不同，所以各自重训一次。库已追加、改在可读时刻重算的旧记录，同一年里的可读时刻相同，同一重训日的几天共用一次拟合。全市场单次拟合在 `V2-P6-014` 实测为 26–125 秒；按每周约 5 条新记录算，每周一次的报告约 2–10 分钟，第一次报告按全部记录数成比例增加。

**前向报告必须显示的内容**（`daily_selection.forward_summary` / `forward_summary_lines`）：

- 首先是 `unverifiable_inputs_corrected_after_filing` 的条数，以及每条记录被更正的分区。
- 然后是两套统计，按角色标明：
  - `headline: the candidate book as listed`：当日列出的候选组合按原样计价的那本账，包含所有期；是候选，不是推荐（`V2-P6-030`；钉在登记提交 `aebaac5` 上的 worktree 仍打印旧标签 `headline: the book as recommended`，含义相同）；
  - `sensitivity: …`：同一本账的各期里，剔除由这类记录开启的那些期（复利净收益、期均净收益、各基准的复利收益）。它是同一条路径的子集，不是重跑：之后各期仍带着被剔除那些期留下的持仓和成本。
  - 两套都要打印，读者才看得出这些更正是否影响结论。
- 接着是显著性检验，两套统计各做一次（fix round 15、16）：用持有期检验自己的函数 `grid.strategy_result`，每套统计只调用一次：对不重叠各期相对登记里 `excess_benchmark` 的净超额（按登记时记下的名字：现行协议是 `equal_weight_all_a_held`，全 A 等权同期持有——一个无摩擦的名义账本，每期执行日开盘卖出上期成员、等额买入本期能买进的全部股票，V2-P6-024；在那之前的登记记的是逐日再平衡的 `equal_weight_all_a`，仍按它读，前瞻账面会把登记记下的基准一并计价；登记里没有 `excess_benchmark` 就拒绝，不用默认值。执行日的 `adj_factor` 或 `stk_limit` 还没入库时这一期基准没有成员，整份前向报告会被拒绝——补建这两个数据集后重跑，见前向周报运行手册）做符号翻转检验（给出单侧 p），`bootstrap_samples`、`random_seed` 取自登记的 settings（缺了、或者是 bool，都拒绝，不用默认值）。000905.SH 取同一个结果的 `reported_*` 键，与单独按它算出的数字相同；按协议它只并列报告，不做检验。只检验完整的期（交易日数不少于登记的调仓间隔）；各期是命令实际调仓的日子，长度未必相等，所以每个被检验的期都打印它的交易日数。较短的期（账面还开着的最后一期、补做调仓后的那一期）在统计里照样显示，但不进检验，输出里写明这一点和被排除的期数。一套统计没有完整的期，或者某个基准没有收益，就写明「不检验」或「不报告」及原因。
- 最后是第一条记录之前无法证明的持有日，以及威胁模型那一句。
- 这类记录照样定价：前向账面就是当时的推荐，在这个威胁模型下，它们是诚实的记录，只是读过的输入后来被上游更正了。

### 记录的结果窗口比账面期晚一个交易日（`V2-P6-012`）

组合记录声明 `horizon = Rd`，它的 `outcome_known_at` 采用标签口径：在信号日之后第一个交易日的收盘入场，再往后数 R 个交易日。账面则是从下一个交易日的开盘持有到下一次调仓日的收盘，按固定网格就是信号日之后第 R 个交易日。所以账面期比记录的结果窗口早结束一个交易日。

两者都成立，只是回答的问题不同：

- 记录的 `outcome_known_at` 是评判它的那个标签何时存在，保持不变。改成 `R-1` 天会让每条已存记录变成另一个声明，而 `0d` 根本不是合法的期限。
- 前向报告判断哪一期已经完整时，用 `strategy_registration.book_period_end`：给它下一次实际调仓日，或者固定网格的间隔。
- 最新一期的终点是固定网格在最新调仓日之后的下一个调仓日（fix round 15）：预定日调仓时就是间隔之后；补做调仓之后更近，就是命令会照常调仓的那个预定日。
- 日历读到下一年（库里有的话），与 `_outcome_calendar` 相同：12 月 31 日的报告要把最新一期的终点放到 1 月，年末那条记录的登记截止时刻（下一交易日 09:15）也在下一年。读不出时报 `ForwardReportError`，不会是未处理的日历错误。

### 前向账面按命令实际调仓的日子定价（`V2-P6-011` / `V2-P6-012`）

**调仓日以只追加的预测库为证，日志只做核对**（第 10、11 轮）。日志是本地文件，改一下就能在真实、按时登记的记录之间挑选交易日。所以前向报告调用 `scripts/daily_selection.py` 的 `forward_rebalances(运行目录, 登记, through=…, as_of=…)`，它从库里重新推出命令的每一个决定（`strategy_registration.witnessed_days`），返回 `ForwardSchedule`：

- **从哪天开始，由库决定**：最早一个带按时、绑定记录的交易日（`first_record`）。
  - 日志第一天晚于它（例如删掉了开头的日志文件），就拒绝，因为那样会让前向账面晚开始。
  - 日志在它之前只能有持有日。这些日子库里什么也没留下，无法与命令没跑的日子区分，所以作为 `unprovable_holds` 原样列出，不计入账面，并在报告输出里写明。
- **排序日**：有一条按时登记、绑定登记的记录的交易日。命令在每个排序日都登记，不管当天调不调仓。
- **持有日**：没有记录。只有同时满足两条才算持有：日志写明命令完成了这一天并且持有，而且把登记配置按那天运行所固定的时刻（日志里的 `as_of`）重新打一遍分（`score_day`，不发请求），确实不排序。
- **没完成的日子**：其他没有记录的交易日。命令下一次运行会补做它的调仓，推导也一样补。
- 在完成的日子上套用与命令相同的 `Schedule`，然后与日志逐日核对决定和记录；任何一天不同，都按名拒绝。
- 回测新增 `rebalance_days`，用它替代固定网格。不传时仍是固定网格，已有结果不变。答案里带着这些日子，所以按指定日子跑的结果不会被当成同一 spec 和来源的网格结果。

实测：

- 1 月 19、21、22、23 日运行、漏掉 20 日：推出 19、21、22 三天和三条记录，回测每次调仓后的持仓都等于命令打印的目标。
- 日志任一方向改动（23 日改成调仓、22 日改成不调仓）被拒绝；删掉 19 日的日志被拒绝；日志指向另一个配置的记录被拒绝。
- 没有记录、配置也会持有的日子：日志写明持有，就算持有日（下一天不补做）；日志没写，就算没完成（下一天补做预定的调仓）。

**剩下的缺口，精确地说**：

- 第一条记录之前的持有日无法证明，只能列出，不能计入。
- 在第一条记录之后，只有一种日子由日志单独决定：配置本来就会持有、但命令那天是否跑过无从证明的交易日。日志说跑过并持有，下一个交易日就不补做；日志没有这一天，就补做。所以在「配置会持有」的预定调仓日之后的那一个交易日，调不调仓由日志决定。这一天库里仍有那条排序记录，改的只是它是否算作调仓；其他任何一天，调不调仓都由库证明。

## 错过的交易日（`V2-P6-032`）

launchd 漏触发（关机、睡眠）、或节假日后第一次运行时，「当天」是最新已收盘交易日，中间的交易日没有人跑过。2026-10-07 实测：研究库因子构建止于 2026-09-25，当天的运行只建了 2026-09-30，2026-09-28、09-29 两个交易日没有截面（manifest 覆盖 2855 个交易日中的 2853），之后的滚动 IC 与 walk-forward 训练窗口会读到这两个时点。这两天已用登记代码手工补建。

**本修复之后的第 4 步**：

- 对配置读到的每个档位，先找它在库里最晚的信号时点，再构建此后到当天（含）的每个交易日（按库里的 `trade_cal`，与因子构建年份同一口径；信号时点是那天 16:30 上海，即 08:30 UTC）。
- 补建了哪些交易日，写在摘要的 `factor catch-up` 一行和当日日志的 `result.factors.caught_up` 里。
- 档位在库里从未构建过时只建当天：历史回填是研究构建的事，不是这一步的。
- **上限 `MAX_CATCH_UP_SESSIONS` = 20 个交易日**（约四周）。按 `V2-P6-006` 实测（三档每个因子每个时点约 1.2 秒），21 个因子每个交易日约 25 秒，补满 20 天约 8 分钟。一个档位错过的交易日超过 20 个时，第 4 步在构建任何东西之前拒绝（退出 1，一行不写）。错误里写出每组档位的缺口范围，以及构建其中最早一批（至多 20 个、同一年内）的 `openalpha factor build` 命令，可以原样运行。跑完再重跑本命令：缺口仍超过 20 个，它就再拒绝一次并给出下一批；不超过 20 个，它自己补完剩下的。
- **补建与拒绝都发生在第 7 步登记之前。** 补建占用的时间计入当天到下一交易日 09:15 的登记窗口；超限拒绝意味着当天的预测**没有登记**。必须在下一交易日 09:15 之前按错误给出的命令分批补建并重跑本命令，过了 09:15 这一天的预测就永久缺失（第 7 步拒绝补登记，见「已知局限」）。正常 18:30 触发、补建至多约 8 分钟时余量充足，风险只在晚跑或大缺口时出现。缺口跨年时按年分批写入：后一年失败会留下前一年已写的部分，重跑即可补完。
- `--factor-gaps`（见下）在"有缺口"和"无法回答"两种情况下都以退出码 1 返回，要按输出的内容区分。
- 它只补「最晚构建之后」的交易日。最晚构建**之前**已经存在的空洞（例如下面钉住的 worktree 漏跑后留下的），第 4 步看不到，要用下面的核对来找。

**钉在登记提交 `aebaac5` 上的 worktree 运行的是登记时的代码，只建当天。** 在登记换到包含本修复的提交之前，漏跑之后应在该 worktree 里，用它自己的环境，对错过的交易日运行一次补建。命令里 `--factor` 对配置读到的每个因子各写一次；`Y` 是错过的那一天所在的年份；`--as-of` 是那天的 16:30 上海（08:30 UTC），同一年里错过的几天可以重复 `--as-of`，一条命令建完：

```bash
"$PWD/.venv/bin/openalpha" factor build --runtime-dir ~/openalpha-research --factor <f>/v1 --tier neutralized \
  --transform cross_section_standard/v1 --neutralization industry_and_size/v1 --year Y-2 --year Y-1 --year Y \
  --exchange SSE --max-staleness-days 30 --as-of <YYYY-MM-DD>T08:30:00+00:00
```

`factor build` 不发 Tushare 请求，不需要 `.env`。不要和每日命令同时运行：两者写同一分区时，后提交的一方整体放弃、一行不写——是这条 `factor build` 就以退出码 6 退出，是每日命令就以退出码 1 退出（`step 4 (factor build) failed: an unexpected fault: PanelWriteConflictError: …`；2026-10-14 更正，此前写的是两者都以 6 退出，见「与其他进程共用面板时」），原样重跑即可。

**怎样判断有没有缺口（只读）**：每日命令新增 `--factor-gaps SINCE`。对配置读到的每个档位，它列出从 `SINCE` 到最新已收盘交易日之间、库里没有构建的每个开市日：拿各档位构建清单（`factor_manifest_*` 及其上面两档的清单）里的信号时点，与 `trade_cal` 的开市日逐日对比。较高一档只在同一时点有较低档位的清单时才算已构建。有缺口时退出 1，没有时退出 0；加 `--json` 输出 JSON。它不准入代码，只从登记文件读配置（并核对文件里的 `config_id`），不发请求，不写任何文件。所以可以在主检出里运行，例如：

```bash
uv run python scripts/daily_selection.py --runtime-dir ~/openalpha-research --factor-gaps 2026-09-01
```

钉住的 worktree 是登记时的代码，没有这个选项。选它而不是一段手写的 Python/duckdb 片段，是因为它与第 4 步共用同一个「某档位在某时点是否已构建」的判断（`_built_instants`），并有测试覆盖（`test_the_factor_gap_check_names_every_session_without_a_build_and_writes_nothing`）。只读的是构建清单，不读因子值；从 2015 年查起，要读每个因子每一年的清单。

## 每天取什么，以及请求预算（R2）

每天取的目标由配置推导（`targets_for`）：

- **基础**（每天）：`trade_cal`、`stock_basic`、`adj_factor`、`price`（`daily`、`daily_basic`、`suspend_d`）、`stk_limit`、`index_daily`（协议基准 000905.SH，前向报告要用）。
- **财报**：只有登记的因子读到的财报数据集才取。
- **行业**（`index_classify`、`index_member_all`）：只在当天的打分会读行业的日子取——中性化档每天（因子构建要读全截面的行业）；行业上限只在调仓日（行业只在调仓决策里被读）。其余日子当天的计算不读任何行业归属，所以「当天打分读到的每只证券」的行业与每天全量刷新完全相同——因为一只也不读。测试 `test_an_industry_cap_refreshed_on_rebalance_days_scores_as_a_daily_full_refresh_does` 把这条规则与每天全量刷新并排跑 5 天（其中非调仓日上游发生一次改类和一次首次归类）：每天的候选榜、目标权重、登记记录完全相同；调仓日两个库对每只证券的行业回答相同。

### 三张报表每天重扫哪些月份（`V2-P6-018`）

规则（`cli.statement_resweep_windows`）：

- **上次构建所在月的前一个月起的每个月**都重扫。每天跑时就是上个月和本月，每月第一次跑时再加上上上个月；中间断了几天、几周，就从断之前那个月的前一个月起全部重扫。
- **更早的月份按星期分成五组**：`(月 − 1) % 5`，周一 1、6、11 月，周二 2、7、12 月，周三 3、8 月，周四 4、9 月，周五 5、10 月；三个公告高峰（4、8、10 月）落在三个不同的日子。每次构建重扫的是**库里分区上次构建之后（不含那天）到今天（含）之间每一个工作日**对应的组：每天跑时就是今天这一组，周一跑时是周一这一组，节假日或漏跑之后把错过的那几天的组一起补上，隔了一周以上就是全年。
- **保证的界（代码实际保证的）：每次构建结束时，它写的那一年的每个月都在过去 7 个日历日内被重扫过。** 所需的状态就是分区覆盖记录里已存的 `as_of`（上一次构建的时刻），不需要新数据集、也不改任何已存的列。理由：一个月若距上次重扫已超过 7 天，这段时间里一定有它那一组的星期几（连续 7 天包含每个星期几）；那一天落在恰好一次构建的区间里，而那次构建会重扫它——只能是本次，否则与「上次重扫」矛盾。连续两个同星期几的假期（2023-09-29 与 2023-10-06 两个周五，2025-10-01 与 10-08 两个周三）只是把那一组推到假期后的第一次构建；漏跑推到下一次运行。不受这个界约束的只有两次运行之间的时间：分区不重建，就不会被重扫。上一版写的「最多两周」是错的——只看构建当天星期几时，上面那两个周五让周五组的月份三周没有重扫。
- **按已存行数预先对半**：重扫已存的月份时，分区覆盖记录里每个公告日的行数是接口返回行数的下界；一个日期窗口的已存行数已经达到上限，就直接对半，不发那次注定被判截断的请求。这不影响任何取回的行，只省请求；补课日的请求数靠它压在 R2 以内。
- **新上市的证券**（上市日不早于库里分区的构建时刻前 30 天）整年一次请求取回（`*_vip` 接口，`ts_code` 逗号连接，年窗口），不参与月份重扫；它们在库里的旧行由这次的回答替换。
- 其余已存行原样带入，按本次的 `as_of` 重新盖入库时刻。

**依据（2026-09-28 实测，18 次在线请求）。** 两次存下的 2026 年分区（2026-09-01 与 2026-09-27 写入，相隔 26 天）逐行比较，再对 2、3、6、12 个月前的已结束月份在线重扫，与两份库逐行（键与值）比较：

- 1–7 月三张报表里，第一次构建之后才出现的行，全部属于这期间新进登记表的 18 只证券（上市日都不早于 9 月 1 日）；没有一行变值，没有一行消失。在线重扫 2026-07、2026-06、2026-03、2025-09 的结果与两份库都相同，只有一处例外。
- 例外：`balancesheet` 的 `000909.SZ`，报告期 2025-12-31，`ann_date` 2026-03-31，`update_flag` 1，`f_ann_date` **2026-09-28**——一条更正，登在六个月前的公告日期下。尾部窗口够不到它；轮转在上次重扫后 7 天内够到。选「每周一天全量重扫」不行：12 月 31 日全量重扫三张报表最多 86 次（2023 年的存量），单日就超出 R2，所以按上面的办法把全量重扫摊到一周五天。

**行业归属按全市场两个状态取（`panel build --industry-sweep states`）。** `index_member_all` 单次上限 3,000 行。2026-09-28 在线实测（80 次请求）：以 31 个一级行业 × 2 个状态的切片取一次作为基准（62 次，7,920 行：当前 5,914、已失效 2,006），全市场 `is_new=N` 一次返回全部 2,006 行（`has_more=False`），全市场 `is_new=Y` 用 `offset` 翻页——`limit=3000` 翻两遍、`limit=2999` 翻两遍——四遍都与基准按全部 11 列逐行相同，无重复行、无重复 `(ts_code, l1_code, in_date)`，四遍的行序也完全相同。于是每次取 4 次请求：当前状态的单次请求在 3,000 行上限处被判为截断，按 2,999 一页再取两页，已失效状态一次。当前状态超过 5,998 行后多一页。

同一天也测了另外两种形状，都不相等，所以没有采用：只给 `l1_code` 不给 `is_new`，只返回该行业的当前归属（`801030.SI` 777 行里只回 464 行）；逗号连接多个 `l1_code`，返回 0 行且 `code=0`。

翻页有一个结构性的盲点：两页之间如果有一条当前归属失效，后面的行整体前移一位，边界上那一行两页都取不到，而且不产生重复。所以全市场的答案在写入前先与库里已存的归属做自检，任何一条不满足就当天改按切片取（多花 62 次请求，`BUDGET` 行写明原因），正确性不打折扣：

- 没有重复的键：每个 `(ts_code, l1_code, in_date)` 的开始行只出现一次、结束行至多一次，没有证券同时有两个当前归属，没有缺了开始行的结束行；
- 库里行业树列出的每个一级行业都至少有一个当前成员；
- 至少有一条已失效的归属（只剩当前快照是写入端的主体守卫唯一看不到的形状）；
- 当前归属数不少于「库里的当前归属数 − 本次答案报告为已结束的那些」；
- 库里的每一条归属都回来了（当前或已结束）。这一条比上一条更强，也正是它能看到翻页的缺口：边界上那一行，除非是上次构建之后才出现的新归属，否则一定是库里已有的。

剩下的盲点：上次构建之后新出现的一条归属，恰好在两页请求之间有另一条失效时落在分页边界上。切片取法也有自己的对应情形（两次切片请求之间发生改类，一只证券可能两边都不在或两边都在）；两者都会在下一次取数时重新取到。离线测试：`tests/unit/test_cli_panel_rules.py` 里的自检逐条测试，以及 `test_a_whole_market_answer_that_fails_the_self_check_is_fetched_again_as_slices`（全市场答案丢一行或重一行时改按切片取，库里的行业回答与前一天相同）。

## 定时（需要你同意后才安装）

定时运行从一个**钉在登记提交上的专用 worktree** 里跑，不从开发检出跑：

```bash
uv run --no-sync python scripts/daily_selection.py --pin-worktree ~/openalpha-daily
```

`--pin-worktree` 读主检出里已提交的登记文件，找到最后一次提交它的那个提交，核对那里的受约束代码与登记的 `code_commit` 完全相同，然后在那个提交上创建（或把已有的、干净的 worktree 移到）一个分离 HEAD 的 worktree。它从不改动有未提交改动的 worktree。登记换了（新的一次研究）就再跑一次它。

**`.env` 链接（`V2-P6-029`）。** uv 会按空格拆分 `--env-file`，而主检出的路径含空格，所以定时运行和手动运行都不写主检出的绝对路径，而是在 worktree 里读相对的 `.env`。`--pin-worktree` 在建好或移动 worktree 之后，在 `<worktree>/.env` 建一个符号链接指向运行 `--pin-worktree` 的那个检出（主检出）的 `<repo>/.env`。只建链接，从不打开 `.env`，所以不读取其中的凭据；`.env` 在 `.gitignore` 里，worktree 的 `git status` 仍然干净。

- 主检出没有 `.env`：不建链接，不报错，打印一行 `no <repo>/.env; nothing was linked …`。建好 `.env` 后再跑一次 `--pin-worktree`。
- 已有指向同一目标的链接：视为已完成，可以重复运行。Windows 上 `os.readlink` 读回的目标带 `\\?\` 前缀（`\\?\C:\...\.env`），比较前先去掉它（`link_text_as_path`，`V2-P6-034`），否则第二次运行会把自己建的链接当成"指向别处"而拒绝。
- worktree 里已有同名的普通文件，或指向别处的链接：拒绝覆盖，退出 1，原样保留。
- 系统不允许建符号链接：拒绝，退出 1，错误里写明原因，不留下任何链接。Windows 上建符号链接需要打开「开发者模式」或在管理员权限的终端里运行，否则会得到 `A required privilege is not held by the client`。

接着它给这个 worktree 建**自己的环境**：`UV_PROJECT_ENVIRONMENT=<worktree>/.venv uv sync --frozen --offline --no-python-downloads --all-extras --python <worktree 的 .python-version> --project <worktree>`。它按 worktree 自己的 `uv.lock` 原样安装、不重新解析。

- **解释器是 worktree 的 `.python-version` 指定的那个**（目前是 3.11）。建成后读回 `.venv/pyvenv.cfg` 里的版本，`major.minor` 不同就拒绝。
- **包含全部 extras**，这样它就是研究时用的环境（`uv sync --all-extras --dev`，dev 组是 uv 的默认）。
- **从不联网**，不下载包，也不下载解释器。uv 缓存里缺哪个包，就按名拒绝，并给出需要你在联网时运行一次的命令（`uv sync --frozen --all-extras --python …`，不带 `--offline`）；这条命令本身从不下载。本机没有对应解释器时，同样拒绝。
- 继承来的 `VIRTUAL_ENV`、`PYTHONPATH`、`UV_PYTHON` 都去掉，所以它不会装进主检出的环境，不会从那里导入，也不会用那里的解释器。

2026-09-28 在草稿目录里对一次性检出（`ce85333` 的导出）实测：离线建成，0.6 秒，全部来自缓存。`pyvenv.cfg` 记录 `version_info = 3.11.14`，环境里是 `numpy 2.4.6`。用这个环境的解释器做第 1 步的比对：装了 66 个包，锁对 3.11 锁定 70 个，0 处差异。`openalpha_cn` 从该检出的 `src/` 导入，没有设 `PYTHONPATH`。第 3 轮那次实测的环境同样是 3.11.14，但没带 extras，所以根本没装 numpy；那次的"0 处差异"不涉及 numpy。

生成 launchd 配置文本（只打印，不安装）。两个任务：**晚间**（工作日 18:30）与**晨查**（工作日 08:30，本机时间）：

```bash
uv run --no-sync python scripts/daily_selection.py --runtime-dir ~/openalpha-research --worktree ~/openalpha-daily --launchd-plist ~/openalpha-research/logs
uv run --no-sync python scripts/daily_selection.py --runtime-dir ~/openalpha-research --worktree ~/openalpha-daily --registration docs/research/survivor.json --launchd-morning-plist ~/openalpha-research/logs
```

两个任务都把 `--registration` 写成参数。不给时默认仍是 `<worktree>/docs/research/p6-registration.json`（P6 的登记）；给了相对名就按 `--worktree` 解析。**登记必须落在钉住的 worktree 内**：解析后落在它之外的绝对路径按名拒绝（退出 2），不会打印出一份去读别的检出的登记的任务。`--launchd-plist` 与 `--launchd-morning-plist` 一次只能给一个。两条命令都只打印文本，没有安装路径：`--install` 是未知参数（退出 2）。

**`--launchd-plist` / `--launchd-morning-plist` 必须在主检出里运行，不要在钉住的 worktree 里运行（`V2-P6-030`）。** 主检出要在含 `V2-P6-029` 修复的提交上（即上面那两条命令，不带 `--pin-worktree`）。钉住的 worktree 是登记时的旧代码：它会把 `<worktree>/.env` 这个符号链接 `.resolve()` 成主检出里含空格的绝对路径写进 `--env-file`，uv 按空格拆分它，生成的定时任务每天都会失败。

配置里没有 shell：`ProgramArguments` 就是 launchd 交给 exec 的参数向量，解释器是钉住的 worktree 自己的 `<worktree>/.venv/bin/python`（`uv run --no-sync` 只用来读 `--env-file`），`WorkingDirectory` 是钉住的 worktree，`EnvironmentVariables` 只设 `UV_PROJECT_ENVIRONMENT=<worktree>/.venv` 和 `PATH`——不设 `PYTHONPATH`，也不指向任何共用环境。

launchd 本身不解析这些路径：路径里的空格、`"` 或 `$` 作为 `ProgramArguments` 的各个参数原样交给 exec。但 **`--env-file` 例外，它是 uv 自己的参数，uv 会按空格拆分它**，所以配置里写的是相对的 `--env-file .env`，不出现任何绝对的 env 路径；它相对 `WorkingDirectory`，即 `--pin-worktree` 建的那个指向主检出 `.env` 的链接。生成配置的 `--env-file` 选项含义与此一致：它是相对 `--worktree` 的名字（默认 `.env`），含空白字符就拒绝（退出 2）并说明 uv 会拆分它，而不会打印出一份必然失败的配置。配置由 `plistlib` 生成（`plutil -lint` 通过）。

测试 `test_the_launchd_job_loads_the_env_file_through_uv_from_a_path_with_spaces` 真的调用 uv：在含空格的目录下，按生成配置的参数和 `WorkingDirectory` 执行，读回只有那个 `.env` 定义的变量。此前的测试只比较参数向量，没有让 uv 读过这个参数，所以没发现这个缺陷。

launchd 不知道交易日历，所以两个任务都按每个工作日触发，由命令自己判断。晚间在 18:30：节假日里「最新已收盘交易日」的日志已经完整，于是只打印摘要，零请求、零写入。1 月 1 日这类假日找到的是上一年的最后一个交易日（日历按当年和上一年两年读）。晨查在 **08:30 本机时间**，对应实测窗口 08:30–09:00 的起点，必须在 09:15 集合竞价之前跑完；它只建议、不改账簿，命令自己会在 `registration_cutoff` 之后拒绝，所以生成命令的机器若不在北京时间，这个任务是失败关闭的，不会在竞价之后误跑。晨查的日志名与晚间分开（`daily-selection.morning.out.log`/`.err.log`）。

launchd 不会替你创建日志目录，加载前需要先建好它。把输出保存为 `~/Library/LaunchAgents/com.openalpha.daily-selection.plist`（晚间）或 `com.openalpha.daily-selection.morning.plist`（晨查）并用 `launchctl` 加载，是安装常驻配置，只在你明确同意后做。不同意就保留手动命令，产物完全相同；状态仍是本节开头的「未启用」，那之前不要安装。

## 已知局限

1. 错过的交易日不能补登记预测：下一交易日 09:15 一到，那天打分的结果就开始揭晓，命令拒绝登记。当天的目标权重仍可通过 `--as-of` 补算，但第 7 步会失败并说明原因。错过的交易日的因子截面则由下一次运行的第 4 步补建（见「错过的交易日」）。
2. 预测在收盘后（约 18:30）登记，晚于 16:30 的信号时点。这样的记录，回测只有在它早于成交日 09:15 登记、绑定登记，并且按它自己的登记时刻（库已追加、那时读不了时，按可读的最早时刻）从已存构建重算一致时才读；重算不一致而它读过的输入在登记后被更正的，记为 `unverifiable_inputs_corrected_after_filing`，照样定价并标出计数；其余拒绝（见上文「回测怎样读这些记录」）。
3. 目标权重是等权 `1 / holding_count` 的决策，不是成交后的持仓：回测里受参与率上限、涨跌停、停牌影响而没成交的单，这里不模拟；上一次的「账面」取的是上一次日志里的目标，而不是实际成交结果。
4. **账面与回测的两种偏离。**
   - 错过或被拒的调仓日：命令在它之后的第一次运行里补做这次调仓（原因写作 `catching up the rebalance scheduled on …`），而不是让旧账面一直留到下一个预定调仓日。补做用的是补做那天的排序，所以那一期与固定网格的回测不同（固定网格在预定日调仓）。前向报告不用固定网格，而是把 `forward_rebalances` 从预测库推出的日子作为 `rebalance_days` 传给回测，所以它定价的正是命令实际推荐的账面。
   - 第一次运行（还没有账面）：当天就建仓，不管当天是不是预定调仓日——回测在那一天已经持有预定调仓日买入的组合，没有账面就无法对齐，等到下一个预定日只会多持有几天现金。
5. walk-forward 模型每天都重训一次：非重训日重训的是最近一个重训日的同一个窗口，结果与回测使用的模型完全相同，但成本每天都付。在策略测试语料（8 只证券）上实测：重训日 `score_day` 0.50 秒，非重训日 0.48 秒，其中 `walk_forward_fits` 0.1–0.2 毫秒，其余是读训练面板；全市场上树模型单次拟合在 `V2-P6-014` 实测为 26–125 秒（47.7 万个样本），即每天付一次这个时间。把拟合好的模型存下来跨天复用需要一个新的持久化契约（树模型没有从制品重建的函数），这一轮没有做。
6. 中性化档的因子构建依赖行业分类的年份覆盖（`V2-P6-015`，本分支已建在它之上）。登记表一侧在一年第一个交易日的缺口（P6 自己的局限）已由 `V2-P7-025` 在本分支上关闭（未推送、未真实运行）：整份登记簿抓取成功、当年还没有上市或退市时，`panel build` 把该生命周期年记成零行分区（输出里有一行 `EMPTY stock_basic year=…`），因子构建读的证券池因此只在当年之内（到 12 月 31 日，含，上海日历日）读作「今年还没有上市或退市」，当年第一条真实事件到来时零行分区被整份替换；失败或截断的抓取、`no_data` 的整份回答、过了窗口的读取、以及已有事件的年在相同或更晚的观测时刻仍按名拒绝；更早的重放什么都不写。真实登记表几乎每周都有事件，但 1 月初并非必然——这正是它曾经停在第 4 步的原因。
7. **上游撤回已存会话的行时，不再让第 2 步停下（`V2-P6-016`，本分支已建在它之上）。** `--incremental` 会重新拉取已存的最后一个会话（一个会话的重叠）。2026-09-28 实测：Tushare 对 2026-08-28 的 `stk_limit` 已不再返回三只基金（`158008.SZ`、`159096.SZ`、`561730.SH`）。现在，重新拉取的会话里少了库里已有的行时，会对该会话再问一次（多 1 次请求）；两次回答一致地缺它，就记为 `upstream_defects` 的 `withdrawn_after_publication`，原行原样存进对应的 `withdrawn_*` 数据集，分区照常写入；增量构建每次还会重问一遍存有这种记录的会话，上游重新发布就撤销记录——与全量构建看到的一样。这些请求只在上游撤回时才发生，不在上面的稳态表里；它们会出现在 `BUDGET` 行和本次运行的请求计数里。撤回只从日期正确的回答里认定。`daily`、`daily_basic`、`suspend_d`、`stk_limit`、`adj_factor` 都是按单个会话请求的，如果回答里有一行日期不是所请求的会话（更早或更晚都算），provider 会以 `invalid_response` 拒绝这份回答，第 2 步停下，什么都不写。这个检查在时点过滤之前运行，否则日期更晚的行会被当作尚不可知而悄悄丢掉。`reconcile_withdrawals` 还会把每份回答与它所请求的那一个会话再核对一次，作为后备。
8. **三张报表增量构建的剩余盲点**：被带入的旧月份若在上游被更正，在它上次重扫后 7 天内进库（每次构建结束时，全年每个月都在过去 7 天内重扫过）；两次运行之间不算——不运行就不重扫。上一年的分区在 1 月以后不再每天构建，登在上一年公告日期下的更正要等一次 `--year Y−1` 的构建（与 `V2-P6-018` 之前相同）。新上市证券的整年回答若漏掉一只库里已有行的证券，问第二次仍漏就按名拒绝，不写。`fina_indicator` 更正一条报告时，是以更晚的公告日期重新发布同一个（证券, 报告期），旧版本不再返回。按**版本**（证券, 报告期, 公告日期）判断：库里的一个版本不再返回、而本次构建在任一公告年里拿到了同一报告更晚的版本，就算被取代——即使同一报告的另一个版本仍留在原公告年里。被取代的版本按 `V2-P6-016` 对撤回行的同一套约定处理：原样存进 `superseded_fina_indicator`（列名 `supersession_confirmed_at`、`original_ingested_time`，之后每次构建按 `V2-P6-003` 重盖入库时刻、原时刻留在 `original_ingested_time`），并在 `upstream_defects` 记一条 `superseded_after_publication`（每只证券每个公告日一条，逐份报告在 `superseded_fina_indicator` 里）；上游之后又在原公告年返回该版本，就撤销这两处记录并把它重新存回。体检把 `superseded_fina_indicator` 当作派生数据集：没有陈旧上限，某年没有分区就是那年没有被取代的版本。库里的版本不再返回、又没有更晚版本的，仍按名拒绝。全量构建和增量构建用同一条规则，所以发生过迁移之后，同一时钟下两种构建写出的字节相同，包括 `superseded_fina_indicator` 和 `upstream_defects`。在此之前，全量重建会因为那一年少一行而被永久拒绝。这两处证据在 `write_financial_statements` 的 `before_write` 里写入，也就是它自己的各项检查全部通过之后：写入被拒，就不留任何证据。某个公告年在库里的 `fina_indicator` 分区缺失或为空，只要它还保留着被取代的版本，同样会被判断：上游又在该年返回的版本照样撤销，其余照样带入。行业自检不通过的那天、以及库里还没有行业归属的第一次，另多花 62 次。
9. **一年的第一个交易日**：当年还没有任何公告时，三张报表与 `fina_indicator` 的当年公告年分区记录为空分区（零行，覆盖记录的 `as_of` 就是观察时刻），读取方回答「还没有公告」；只在当年第一个法定披露截止日（4 月 30 日）之前允许，之后空年份按取数失败拒绝。库里的实测（2014–2026）：当年第一条公告晚于第一个交易日的有 2020、2023、2024 三年。空分区与普通分区一样受新鲜度约束：观察时刻比读取方允许的陈旧上限更早就拒绝，不会把一月的「没有公告」当成三月的答案。 读取时同样执行截止日规则：4 月 30 日之后，读取方遇到空的公告年分区就按「陈旧」拒绝，即使没有设陈旧上限。
10. **`pre_close` 与复权因子对某个会话说法不一时，由 `upstream_defects` 裁决（`V2-P6-020`）。** 某个会话的 `daily.pre_close` 与 `adj_factor` 推出的前收盘价不一致、超出两者发布精度（每个因子按自身取值取 tick：能用三位小数表示的取 1e-3，否则取 1e-4）时，`stk_limit` 目标会按当天的涨跌停带裁决：带的中心落在哪个说法上、且当天收盘价在带内，就认定那个说法；两个都不成立，这个会话的收益就是“不可知”。裁决前要逐只证券重新拉取这一对会话的两根 bar 和两个因子（每对 4 次请求），与库里一致才记录；发出第一个请求之前先打印一行 `BUDGET return-path-reproduction 4×N requests`，`--return-paths-from-store` 也一样。构建报告里这三种记录标为 `recorded`（不是 `dropped`），数值写作 `implied_pre_close=`（`--json` 里的键同名），因为什么都没有丢弃，这个值是复权因子推出的前收盘价。
   - **重建依赖。** 裁决读的是库里已存的 `daily`、`adj_factor` 和 `stk_limit`。所以，某年的 `daily` 或 `adj_factor` 重建之后，必须再对**同一年和下一年**重新裁决：下一年第一对会话的前收盘价在这一年。可以重建 `stk_limit` 目标，也可以只跑不拉涨跌停带的裁决：`openalpha panel build --dataset stk_limit --year Y --return-paths-from-store`。后者只读库里的三个数据集，每个有分歧的会话对 4 次请求，只替换 `upstream_defects` 里的裁决行，`stk_limit` 目标的其他记录（停牌日的 0/0 带、撤回）原样保留。
   - **重新拉取与库里不一致时。** 这一年的 `stk_limit` 写入被拒绝，报错里点名是哪只证券、哪个会话、哪个数据集；什么都不写。处理办法是重建报错里点名的数据集（`daily` 或 `adj_factor`）的那一年，再裁决一次。
   - **增量构建。** 每次都用库里的数据把全年的会话对裁决一遍。库里已有的裁决与现在的数据完全一致时直接沿用，不重新拉取，所以只有本次切片里的分歧、以及因数据变化而改变的旧裁决，才会花请求。上一年只为两类证券读取：本年第一对会话落在本次切片里的，以及库里已经存有第一对会话裁决的。后者要重新判断，因为裁决同时依赖前一天的收盘价、`pre_close` 和两个因子，其中两项在上一年；上一年重建过，这对会话就会按现在的数据重新裁决。
   - **读取方。** 标签、`factor run`、`factor_ic_series`、trailing-IC、walk-forward、策略账本、价格收益类因子和 panel doctor 都按同一份记录执行。印证的一方就是这个会话的收益。不可知的会话会让跨越它的标签被丢弃并计数；价格收益类因子（动量、反转、波动率、Amihud、残差波动率）在跨越它的窗口上给出 `undefined_value`，并在 `factor build` 的 `unknowable_return_sessions` 里列出；账本按复权因子路径计值，并在结果的 `unknowable_crossings` 里给出与发布路径相差的金额和占账面的比例；doctor 仍会报告，说明收益不可知。没有记录的分歧仍然拒绝。
   - **已存的因子构建。** 裁决不是因子构建清单（manifest）的输入，所以在裁决写入之前构建的因子分区不会被任何就绪检查、陈旧检查或 doctor 发现：它们仍是发布路径上的值，而引擎现在会在不可知的会话上给出 `undefined_value`、在认定复权路径的会话上按复权路径计算。按下面的顺序处理：
     1. 裁决：`openalpha panel build --runtime-dir R --start Y0 --end Y1 --dataset stk_limit --return-paths-from-store`（只读库里的数据集，按 `BUDGET return-path-reproduction` 行所说的次数重新拉取）。
     2. 检查：`openalpha factor stale-return-paths --runtime-dir R --exchange SSE --max-staleness-days N`，`N` 用构建这些因子时的同一个值（本仓库的构建都用 30）。它只重算裁决可能改变的已存观测：观测自己记录的窗口（`input_session_first`–`input_session_last`）里、引擎确实读取的会话上有裁决——`computed` 值只看“不可知”裁决，以及读自身 `pre_close` 的因子上的复权路径裁决（`published` 裁决不改变已存值，逐日收盘价收益也不读 `pre_close`）；`undefined_value` 看任何裁决。逐日收盘价收益窗口的第一个会话、以及动量跳过的最新 5 个会话里的裁决不算。开始重算之前先打印 `BUDGET stale-return-path-recompute N compute_factor calls`；每次调用在该构建自己的时点读它的分区年份，同一 (因子, 年份) 内共用一次增量读取。按评审估算，研究库在收窄后约 263 次（收窄前约 4,556 次，其中约 94% 来自 `published` 裁决）；修复后再跑一次，同样的构建会因为存的是 `undefined_value` 而被再算一遍，次数相近，但不会再列出。与库里的值不同就列出 `(factor, tier, year, as_of, manifest_id)`，每条后面写“与引擎当前结果不同；某裁决落在它的窗口内”——这只说明为什么被重算，输入分区重建过也会出现在这里，修复方法相同——以及修复它的 `factor build … --supersedes-raw/--supersedes-processed/--supersedes-neutralized` 命令（每个 transform 一条，raw 只由第一条取代），退出码 1；没有就打印 `stale return-path builds: none`，退出码 0。
     3. 按打印的顺序逐条运行这些命令，然后再跑一次第 2 步，直到它回答 `none`。
     **检测不到的一种情况。** 重建 `daily` 或 `adj_factor` 之后两种说法变得一致，重新裁决就不再为该会话记录任何裁决；此前因“不可知”而存为 `undefined_value` 的因子值于是窗口里没有裁决，检测命令看不到它——库里不保留被替换的裁决，裁决也不是 manifest 的输入。重新裁决（`--return-paths-from-store` 或 `stk_limit` 目标）会在 stderr 上为每个这样的裁决打印一行 `RETIRED-RETURN-PATH <证券> <会话> was <kind>`，这是唯一知道它的时刻：看到这一行，就对窗口包含该会话的价格收益类因子（动量、反转、波动率、Amihud、残差波动率）重建对应年份，带上 `factor stale-return-paths` 同样格式的 `--supersedes-*`（用 `load_factor_manifests` 读出要取代的 manifest）。
     这不是 doctor 的检查项：doctor 只能依赖 `panel_ingest`（分层规则），而判断一个因子值是否变了必须调用因子引擎。
11. **年界上的潜在缺陷（P6 形态，未修）。** 第 2 步只建当天所在的年份：上一年漏跑了最后几天、而新一年的第一次构建照常进行时，新一年第一次 `stk_limit` 构建会拿每只证券年初的第一对会话去对一个不是前一交易日的收盘价，有分歧的每一对都按 4 次请求重新拉取、不设上限（实盘规模约 2 万次请求），之后 doctor 的年初检查卡在这个缺口上。幸存者形态的第 2 步在发请求之前按名拒绝这种情形（见下）；P6 形态要保持逐字节不变，没有改，P6 的每日恢复之前要另立任务处理。

## 幸存者形态（`kind: "survivor_book/v1"`，`V2-P7-008`）

> **状态：未启用。** 幸存者配置还没有登记，它在 `V2-P7-006`（协议与预登记）由用户确认之后登记一次。在用户明确确认那次登记之前：不要运行晚间，也不要运行清晨复核；不要安装 launchd；不要为恢复手工补面板（要数百次 Tushare 请求，须经用户同意）。本节描述的是代码现在实际做什么，供恢复时照做。它不是研究结论：记录是一个已登记研究配置的「候选」预测，没有下过任何单，纸面账簿的权益不是证据。**例外：`V2-P7-019` 的真实数据冒烟**（一次性克隆里的冒烟登记、自己的运行目录，只经 `scripts/p7_smoke.py`、经用户逐步同意），见文末「真实数据冒烟（`V2-P7-019`）」。

### 分派与登记的形状

第 1 步准入与 P6 相同（登记已提交、代码与环境绑定、`config_id` 按 `config` 重算一致）。之后，`config` 写明 `kind` 的登记交给 `strategy_survivor` 读取，跑下面的九步；没有 `kind` 的仍是上文的 P6 八步。

- 顶层键只能是 `kind`、`survivor_book`、`adapter` 三个。`adapter` 块（`survivor-adapter/v1`，多一个键就拒绝）：`schema_version`、`epoch_session`、`exchange`（只能 `SSE`）、`transform`、`min_coverage`（大于 0、不超过 1）、`max_carry_sessions`、`max_panel_catch_up_sessions`（0 到 16 的整数，必须写，没有缺省值）、`benchmark`（只能 `000905.SH`）、`prediction_horizon`（`20d`）、`cost_policy`（`protocol/v1`）、`paper_limits`、`unfilled_buy`（`reject_whole_and_carry/v1`）。
- 未知的 `kind`、多出或缺少的顶层键、读不通的块：第 1 步，退出 2，0 次请求。
- `survivor_book.seed` 与登记 `settings.random_seed` 不一致：第 1 步，退出 3——登记在，但自相矛盾，与 `config_id` 对不上同一类（settings 没有整数的 `random_seed` 时按 0 比较，拒绝信息里说登记没有给 `random_seed`）。
- 前向周报还要读登记 settings 里的 `survivor_forward_protocol` 块（`V2-P7-006` 冻结）；每日命令不读它。

### 前提

1. 同 P6 前提 1–3、5，登记文件用 `--registration` 指向幸存者登记（默认仍是 `docs/research/p6-registration.json`）。
2. 面板里 `namechange` 与 `trade_cal` 从各自第一个已存年起逐年连续；面板落后最新已收盘交易日不超过 `max_panel_catch_up_sessions` 个交易日，否则第 2 步拒绝（见「重启」）。
3. `adapter.epoch_session` 是第一次计划运行的**前一个**交易日，必须是已存日历里的开市日；还没有纸面账簿时，纪元到当天最多相隔 `1 + max_panel_catch_up_sessions` 个交易日。
4. 运行目录在本地文件系统上（纸面账簿的写锁是建议锁，NFS、SMB 上只和服务器的锁管理一样可靠），当前账户可写，支持硬链接：纸面账簿的标记 `RT/paper/registration.json` 与每条记录的输入溯源 `RT/daily_survivor_provenance/<摘要>.json` 都按「写本次运行自己的临时文件、同步、硬链接到名字、再同步目录」写入，所以要么整份在、要么不在；FAT、exFAT 和很多网络盘做不到，按名拒绝（标记在第 5 步，溯源在第 7 步，见下表）。

### 手动运行

在钉住的 worktree 里，同 P6 的「手动运行」，加上幸存者登记：

UV_PROJECT_ENVIRONMENT="$PWD/.venv" uv run --no-sync --env-file .env "$PWD/.venv/bin/python" scripts/daily_selection.py --runtime-dir ~/openalpha-research --registration <幸存者登记文件>

### 选项

| 选项 | 幸存者形态 |
|---|---|
| `--full-update` | 拒绝：第 1 步，退出 2，什么都不做（整年全量刷新是 `openalpha panel build` 的事，不是一天的事） |
| `--top` | 拒绝，同上（幸存者形态不打印候选榜，纸面账簿的计划整份打印） |
| `--dataset T` | 只能是当天目标 `targets_for_survivor` 的**超集**——四个组合因子时是 `trade_cal`、`stock_basic`、`adj_factor`、`price`、`stk_limit`、`namechange`、`index_daily`：可以多加，不能少；少一个就拒绝（第 1 步，退出 2），因为记录不能从当天没有更新过的面板上登记 |
| `--max-staleness-days N` | 第 4 步因子构建的新鲜度上限，同 P6 |
| `--as-of ISO` | 钉住**第一次运行**的时钟，也由它找出「当天」是哪个交易日（那一刻已发布的最新交易日）；这个交易日已有日志时，重跑一律用日志里钉住的时刻，`--as-of` 只用来找交易日 |
| `--json` | 打印当天的结果文档；被第 8 步拒绝的一天，打印到停下为止的文档 |
| `--morning-recheck` | 清晨复核，见下 |
| `--factor-gaps SINCE` | 不适用：幸存者登记没有 `start`，输出 `factor gaps: the registered configuration cannot be read: 'start'`，退出 1（只读，不写任何文件）；幸存者形态的因子缺口由第 4 步自己补——只补各档位最晚构建之后的，至多 20 个交易日 |

| `--pin-worktree`、`--launchd-plist`、`--launchd-morning-plist` | 不进入任何一天，与 P6 相同；两个 launchd 选项见「定时」 |

**查看账簿当前持仓（只读）。** `--show-book` 只读运行目录里 `paper/snapshots` 的最新快照（`--runtime-dir` 必填），打印现金、每只持仓的批次与成本、最后标记与账本权益，然后退出：零写入、零请求、不开面板、不加载 `build_storage`，所以能在主检出里安全运行。它不核对登记、也不推进账簿；`--registration` 只用来决定要不要带冒烟横幅，与运行目录里是哪本账簿无关。运行目录里没有快照或快照损坏时按名拒绝（退出 1），绝不把「没有账簿」当成「空账簿」开始读。**标记是账簿单位**（真实收盘价乘以自买入以来的复权比例），不是真实收盘价。冒烟登记（`settings.smoke_run`）的每一份输出——文本的首尾行与 JSON 的 `smoke` 键——都带冒烟横幅，被拒绝时也一样。例：

```bash
uv run python scripts/daily_selection.py --runtime-dir ~/openalpha-research --registration <幸存者登记文件> --show-book
```

**记录账户实际成交（对账输入，`V2-P7-006a`）。** 纸面账簿假设晚间印出的每张单都下了、都在开盘成交；真实账户可能不同。把用户当天的实际下单与成交写进一份 JSON，放在 `RT/paper/account-record/<交易日>.json`（用户文件，永不入库、不进 git），这一天的第 8 步会在账簿推进**之前**读它，与当天到期的订单逐张比较，把分歧**按名记进当天 journal 的 `result`**：`not_placed`、`filled_where_the_book_did_not`、`quantity_differs`、`price_differs`。分歧只**记录**，从不改写纸面账簿：账簿仍按自己的假设推进，真正的账户同步在 `006b` 之后。记录是可选输入；缺一整份记录不是一致，摘要会写明账簿的假设未核对。**在 `006b` 之后才按用户的运维纪律逐日使用**；本项不是真钱闸门，真钱闸门仍然关闭。

格式（`account-record/v1`）：

```json
{"schema_version": "account-record/v1",
 "session": "2026-04-07",
 "orders": [
   {"order_id": "sbo_...", "ts_code": "600000.SH", "side": "buy",
    "placed": true, "filled_quantity": 1000, "filled_price": "10.20"}
 ]}
```

- 一条到期订单一行：**当日在册的每张订单必须恰有一行**（缺行是拒绝，不是默认同意）；同一 `order_id` 不得出现两次；`ts_code` 与 `side` 必须与计划一致；**买入**的 `filled_quantity` 不得超过计划数量。
- **卖出只核对是否成交，不核对股数和价格**：账本里卖出的股数是**账本单位**、卖出价是 `开盘价 × 复权比例`（摘要的 Units 一段）；送股/拆股后账本股数不等于账户股数，现金分红等任何复权事件之后账本价格也不等于真实价格，而卖出永远是「SELL ENTIRE POSITION」，所以卖出行只要两边都成交（或都没成交）就是一致，账户记录的真实股数与真实价格不参与比较、也不会因此报分歧；买入按 ratio 1 用真实单位，股数与价格照旧全部核对。
- `placed: false` ⇒ 数量为 0、没有价格；数量为 0 ⇒ 没有价格（`filled_price` 省略或为 `null`）；有成交则必须有价格。
- 记录文件里同一条 `order_id` 出现两次，文件本身读不出（`AccountRecordError`，是 `ValueError` 的子类）；其余不可比的记录——记的不是这一交易日、出现当日晚间没有计划的订单、缺行、方向或代码不符、**买入**数量超过计划——是 `AccountRecordConflict`。两者都在第 8 步账簿推进前**按名拒绝**（退出 1，不落快照、不写账本行）；修好记录后重跑同一天即可。
- `--account-record PATH` 指定别处的一份记录（给了却不存在同样按名拒绝）；不给时找 `<RT>/paper/account-record/<交易日>.json`。
- **没有记录不是一致**：没有文件时，摘要的 RECONCILIATION 一栏（结账日没有晚间块，同一句印在当天 catch-up 条目下）写 `no account record for <交易日>: the paper book's assumption that every printed order was placed stands unverified`（账簿假设未核对），绝不补零。
- 一份记录的拒绝与一行分歧都只让这一天**停下**（拒绝）或**被记下**（分歧），不改变纸面账簿的推进语义。

1. `no new orders were produced tonight`。若纸面账簿在这次拒绝之前已经提交了这一天的晚间，改为 `the paper book committed the evening of <交易日> before this refusal (<快照 id>): its plan for the open of <开盘日> stands, and the paper book fills it at that open whether or not it is placed:`，下面列的就是那份计划。
2. 纸面账簿为下一个开盘仍持有的有效单（在那个开盘之前就到期的买单不列）：一行标题，例如 `orders the paper book holds live from its last settled session, <日期> (it settles the open of <交易日> with them first): place again for the open of <开盘日> each one your account did not fill:`，下面每张一行——`SELL ENTIRE POSITION <代码> (ledger qty <账本数量>) <原因>, planned on <日期>; a sale never expires`，`BUY <代码> <股数> shares <原因>, planned on <日期> at <计划价>, live through <日期>`。没有有效单写 `the paper book holds no order live for the open of <开盘日>`；还没有账簿写 `the paper book holds no live order: it has settled no session yet`；读不出账簿写 `the paper book's live orders could not be read (<原因>); they are the orders the last evening printed, less any your account filled`。
3. 期限。下一交易日 09:15 之前：`rerun before <09:15 的时刻，+08:00>, the call auction of <开盘日>, with:`，下一行是重跑这一天的完整命令（「手动运行」的形式；这次运行给了的 `--as-of`（换成上海时间）、`--dataset`、`--json`，以及不是缺省值的 `--repo`、`--max-staleness-days` 都照抄），再一行 `after that, the next run settles <交易日> without a decision`。已到 09:15：`the call auction of <开盘日> began <时刻>: a rerun can no longer decide <交易日>, and the next run settles it without a decision`。晚间已提交的那种：09:15 之前是 `rerun before …, the call auction of <开盘日>, to complete this day's journal and print the plan, with:` 加命令；之后是 `the call auction of <开盘日> began <时刻>: the paper book fills that plan there whether or not it was placed; the refusal above says how this day's journal is completed`。

### 运行目录里的文件

- `RT/daily_survivor/<config_id 前 16 位>/<交易日>.json`：当日日志（`openalpha-daily-survivor/v1`），与 P6 的 `RT/daily_selection/` 分开。写入顺序：`as_of`、`held`、`held_from`、`registration`（任何请求之前）→ `panel` → `factors` → `prediction` → `catch_ups`（每补结算一个交易日写一次）→ `paper` 与 `result`（只在这一天完成时写）。
- `RT/daily_survivor/<config_id 前 16 位>/<交易日>.morning.json` 与 `<交易日>.morning.<YYYY-MM-DD>.json`：清晨复核的文件，放在晚间日志旁边——第一次复核是前者，之后每个更晚的上海日历日各一份后者（见「清晨复核」）。读这个目录的程序只能读 `YYYY-MM-DD.json` 这样的名字（前向周报就是这样读的），**不要按 `*.json` 通配**。
- `RT/daily_survivor_provenance/<摘要>.json`：每条记录的输入溯源（`daily-survivor-input-provenance/v1`），按内容寻址、只写一次，在记录之前写，整份链接到名字（见「前提」4）；晚到记录核查按（交易日，批次摘要）找它。
- `RT/paper/`：纸面账簿。`registration.json` 是只写一次的标记（`config_id`、账簿配置摘要、纪元、登记文件的 `registration_sha256`），把这个运行目录的账簿绑定到**这一份登记文件**：同一配置的另一次登记就是另一本账，要另一个运行目录；`writer.lock` 是单写者锁，持有者退出（包括崩溃）时内核即释放；`snapshots/<交易日>.<snapshot_id>.json` 每个已结算交易日一份，只写一次；`ledger.sqlite3` 是纸面账簿自己的账本。
- `RT/predictions/`：预测库，与 P6 共用；`RT/reports/`：前向周报与它的核查缓存。
- 备份时 `RT/paper/`、`RT/daily_survivor/`、`RT/daily_survivor_provenance/` 与 `RT/predictions/` **一起**做：下面的补救都假定它们出自同一份备份。

### 一天是哪一种：晚间、只结算、补结算

一天走哪条路，由**日志里钉住的 `as_of`** 决定，从不看这次运行的时钟：钉住的时刻早于下一交易日 09:15（集合竞价开始，`registration_cutoff`）就是晚间，等于或晚于它就是只结算。第一次运行钉住的是 `--as-of` 或当时的时钟；同一交易日之后的每次重跑都用它，所以重跑永远是同一种日子。

- **晚间**：第 7 步登记记录；第 8 步先补结算，再结算当天、做决定、为下一交易日的开盘计划订单。
- **只结算**：第 6 步照样读事实（覆盖率下限为 0，没有可入选证券也不拒绝，持仓状态照样要用），第 7 步不登记，第 8 步补结算并只结算当天、不做决定。摘要的 ORDERS 一栏写 `NONE PLANNED tonight -- no evening was run`，并说当天已在今晚结算、没有决定。
- **补结算**（两种日子都会有）：账簿缺的每个交易日（某一晚没跑，或被拒、没有提交）在当天之前按顺序结算，不做决定、不登记；每个交易日单独提交，提交后马上记进日志。中途停下，已结算的保留；一个已提交却没来得及记进日志的交易日，下一次运行先重新推导它（不写任何东西）再记入，摘要的 catch-up 一行写 `re-derived after an interrupted journal`。
- **纪元当天**：只开账（第一份快照和标记），不读事实、不登记，退出 0；第一晚是下一个交易日。
- **已提交、日志没写完**（上次运行在快照与日志之间停下）：这次运行不跑第 3、4 步，用日志钉住的输入重新推导这一晚，纸面账簿一字不写，然后把日志补完；晚间日的 ORDERS 标题写 `evening unchanged (settled earlier; derived again, nothing written)`。

### 在下一交易日 09:15 之前跑完

- 每个交易日收盘后（约 18:30）运行一次，在下一交易日 09:15 之前跑完。
- 晚间日到 09:15 还没提交：还没登记记录的，第 7 步拒绝；已登记的，第 8 步拒绝，信息里写 `the call auction of the next session has passed, and nothing was decided or written`。退出 1，什么都不决定、不写。**不要重跑**：下一交易日的那次运行会把这一天补结算掉，不做决定；已登记的记录照样有效。
- 第一次运行就在 09:15 或之后（例如第二天上午补跑）：这一天是只结算日，不登记、不决定，摘要写 `NONE PLANNED tonight`，并说这个交易日今晚已结算、没有决定。
- 已提交的晚间在 09:15 或之后补完或重印时，ORDERS 标题下多一行 `the call auction of <日期> has passed (it began …): these orders were for it, and this run was made after it -- the paper book fills them at that open whether or not they were placed`。纸面账簿在那个开盘按计划成交，不管你下没下单；你没下的话，账户与纸面账簿从那天起分叉——记下来。

### 订单怎么读

摘要先给要照着做的，再给这次运行怎么读的数据。依次是：session、ORDERS、carried orders、unfunded、unaffordable、deferred exits、near exit、frozen、watch list、illiquid exits、positions、book、settled、catch-up；然后是一行标题 `diagnostics        how the run read its data -- nothing below is an order`，其下是 ids、facts、screen、prediction、（补建了的话）panel catch-up 与 factor catch-up、tushare requests、units；最后是 wording。空的一栏打印 `none`，不会因为没有一行而被读成「没事可做」。摘要里的每个时刻都按上海时间打印，不管它是怎样存的。

- **session**：`<交易日> (as of <钉住的时刻，+08:00>)`。不带 `--as-of` 运行、而今天不是这个交易日时，下一行说为什么是它：`today, <日期>, is not a trading day: <交易日> is the last trading day`（周末、假日），或 `today, <日期>, is a trading day whose data is published at 16:30: <交易日> is the last complete session`（交易日 16:30 之前）。这一行只打印、不存进日志。
- **ORDERS 标题**：`ORDERS FOR THE OPEN OF D+1 (call auction 09:15), <开盘日> -- evening created`（重新推导时是 `evening unchanged (settled earlier; derived again, nothing written)`）。交易清单的 id 不在标题里，在 diagnostics 的 `ids` 一行（`session index <序号>; trade list <id>; paper snapshot <id>`）；`--json` 里每个 id 都在。
- 标题下（晚跑时先有「集合竞价已过」那一行，见上一节）是两行说明。一行是 `real closes are references, not limit prices; the paper book fills at the open`。另一行是限价说明：`at the 09:15 call auction an order carries a limit price: this system assumes that a buy placed at its limit-up price and a sell placed at its limit-down price take the single opening price -- confirm with your broker. Each limit below is computed from the real close (main board 10%; ST 5% before 2025-07-07, 10% from it); the exchange's published limit governs`。这是**本系统的假设**，不是哪家券商的规则：集合竞价收的是限价单，买单挂下一交易日的涨停价、卖单挂跌停价，就以唯一的开盘价成交。**下单之前向你的券商确认。** 每张单后面的涨停价、跌停价，用的是纸面账簿成交时用的同一个函数（`backtest.execution.derived_price_band`），从今晚的真实收盘价算出，四舍五入到分：主板 10%；ST 在 2025-07-07 之前 5%，从那天起 10%（代码里的 `BAND_WITNESS_ENDS`，按单子要成交的那个开盘日判断）；以交易所公布的涨跌停价为准。算不出时写 `no limit computed: <原因>`（今晚没有真实收盘价；或者卖单的名字筛选里没有结论，不知道它是不是 ST）。
- **顺序**：先是今晚的卖单，再是从更早交易日顺延、纸面账簿里仍有效的卖单与买单（`REPEAT`），最后是今晚的买单。内核给买单分钱也是这个顺序：先顺延的，后今晚的。
- **卖**：`SELL ENTIRE POSITION <代码> (ledger qty <账本数量>; real close <收盘价>) <原因> (<筛选原因>); limit-down <跌停价>`，停牌的在收盘价那个括号后加 `(suspended: the close may be an earlier session's)`。**一律卖出全部持仓**；账本数量是账本单位，不是要卖的股数。
- **买**：`BUY <代码> <股数> shares, about <金额> yuan -- reference: real close <收盘价> <原因>, live through <日期>; limit-up <涨停价>, <金额> yuan at it`。股数是**在 09:15 用当时的现金、按下一交易日涨停价能冻结的整手数**：等权目标按真实收盘价算（350,000 元现金、10 只等权时每只 34,825 元），但现金买不到那么多时，股数就少于等权本可买到的股数，少多少在资金行下面按名字写出来。`about … yuan` 是按收盘价算的整数元，`… yuan at it` 是按涨停价算到分的金额（挂涨停价的单，券商冻结的资金按它算）。收盘价只是参考；纸面账簿按开盘价成交。
- **REPEAT**：更早的晚间计划、纸面账簿还没成交的单，下一个开盘再试一次。券商的单只当天有效，所以每晚都要重新下，除非你的账户已经成交。买单：`REPEAT BUY <代码> <股数> shares, about <金额> yuan (planned on <日期> at <计划价>; real close today <收盘价>) <原因>, live through <日期>, attempt a of n (one per session; a session with no bar counts) -- not filled in the paper book: re-place it for the open of <开盘日> unless your account filled it; limit-up …`。卖单：`REPEAT SELL ENTIRE POSITION <代码> (ledger qty …; real close …) <原因>, planned on <日期>, attempt a, a sale never expires -- not filled in the paper book: re-place it for the open of <开盘日> unless your account sold it; limit-down …`。下面的 carried orders 一栏只写个数：`N live orders from earlier sessions, repeated in ORDERS above`。
- **资金**：有买单时，单子后面一行 `cash at 09:15 <X> yuan; buys freeze <Y> yuan at their limit-up prices (1.10x the reference, the main board's band); sells tonight release about <Z> yuan after the auction, not before it`（有一张买单算不出涨停价时，`buys freeze` 后面的总额不打印，免得把缺一张的数当成全部）。内核只用 **09:15 的现金**给今晚的买单定量，并按每张买单的**涨停价**冻结：`FREEZE_RATIO = 1.10`、基准是信号日收盘、四舍五入到分（**这是本系统的假设，不是已确认的券商规则，下单前向你的券商确认**）。今晚卖单的回款在**同一个**集合竞价里、在买单被冻结**之后**才到，所以**不计入**现金。350,000 元、10 只等权（每只 34,825 元）时，十张涨停价买单要冻结约 38.5 万元、超过现金：清单把最后一只写成更小的股数（`FREEZE_SHORTFALL_POLICY = "reduce_lots"`；改成 `"drop_whole"` 就整只不买），并在资金行下面按名字打印短少（`  <代码>: <实际股数> of the <等权股数> shares the equal share asks; <金额> yuan short at the limit-up price`）。买单在内核里按分钱的顺序累加（先顺延的，再今晚的），累计超过现金的那张下面标 `is not covered by the cash at 09:15 (the plan asks for more than the account holds; do not place it)`：这只应出现在清单与账户现金不一致的缺陷场景，正常晚间不会出现。回款只算今晚的卖单（顺延的卖单什么时候成交不知道，内核不算它）。
- **账户与纸面账簿的分叉**：有单时，单子与资金那一行后面是 `the paper book assumes every order above is placed and fills at the open; your account follows the book only if you did exactly that`；有卖单时再加一行 `a SELL above of a name your account does not hold (you did not buy it -- for example, you followed this morning's re-check): ignore that SELL`。今晚没有新单时写 `no new order planned tonight`（有顺延单时接着写 `; N carried orders repeated above`）。settled 与 catch-up 里，被拒或过期的买单后面写 `if your real order did fill, the paper book does not hold it and will never print a SELL for it`；核销写 `<代码> written off (ledger qty <数量>): whole cost basis <金额>, no price -- the paper book wrote it off; your account may still hold the shares, and no SELL will be printed for them again`。这些都记下来：账户与纸面账簿从那天起不同（见「已知局限」）。清单可执行不等于账户一定与账簿一致：09:15 的现金是账簿的模型、不是账户真值，账户对齐靠 `006a` 的账户成交对账（尚未做），所以真钱闸门仍然关闭。
- **deferred exits、near exit、frozen** 各带一句它对账户的意思。deferred exits：`left the survivors; kept tonight because tonight's sales reached the cap: no order -- do not sell it; the paper book sells it at a later evening`。near exit：`held and still a survivor, near the survivor cut: information only, no order`。frozen：`held and halted: left alone until it trades again, no order`。watch list、unfunded、unaffordable 后面的 `today's draw, not a promise for tomorrow`：今天的抽签，不是明天的承诺。
- **positions**：每只一行 `<代码>  ledger qty <账本数量>  real close <收盘价>  ledger/real ratio <比>`，停牌的加 `(suspended: …)`，后面是状态 `frozen`、`near exit`、`no bar since <日期> (marked at its last price)`（以前写作 `carried since`，现在说的是它从哪天起没有日线、按最后价格估值）。`ledger/real ratio` 是买入以来的复权比，**包括现金分红**，不是股数乘数。现金分红之后账户里是买入的股数加上现金：1000 股、25.00 的收盘派 0.50，比值 1.0204，仍是 1000 股，不是 1020.4 股。只有送股、拆分之后，账户的股数才与账本数量不同。所以卖出永远用 SELL ENTIRE POSITION。
- **book**：`equity …, cash …, gross exposure …, N holdings; ledger equity is not evidence`。
- **diagnostics** 下的 facts 一行末尾 `book holdings before tonight's fills N`（以前写作 `held N`）是日志钉住的持仓只数：当晚成交与结算之前的账簿，第一晚是 0。账簿现在持有什么，看 positions。

### 清晨复核（`--morning-recheck`）

在晚间之后、下一交易日 09:15 之前运行（例如 08:30），同样在钉住的 worktree 里：

```bash
UV_PROJECT_ENVIRONMENT="$PWD/.venv" uv run --no-sync --env-file .env "$PWD/.venv/bin/python" scripts/daily_selection.py --runtime-dir ~/openalpha-research --registration <幸存者登记文件> --morning-recheck
```

它复核的是这次运行的时钟（或 `--as-of`）那一刻已发布的最新交易日那一晚的计划。加 `--json` 打印这次运行的清晨文件本身（最新的一代）。它总是发**一次** Tushare 请求：那个交易日所在年份的 `namechange`（新年也只问这一年，因为事实适配器不读之后的年份；年初首晚之后的清晨，当年还没有更名公告时上游回答为空，照样把当年记成零行分区、不拒绝，`V2-P7-021`）。取数之后，它在清晨的时钟上把那个交易日的事实再读一遍，与晚间读到的比较，把与那一晚计划不同的地方打印为**建议**。晚间读到的是什么：第一次复核在取数**之前**用当晚自己钉住的时钟和持仓把当晚的事实再读一遍，并与当晚的文档核对；之后的复核沿用前一次存下的那份（见下）。纸面账簿从不改变（决定：账簿按晚间的计划走，分歧只记录、只打印）。它只写清晨文件、`namechange` 分区和面板的 catalog（分区登记）；预测库、账本、快照、晚间日志与溯源文件都不碰；措辞是「已登记研究配置的候选；没有下单；纸面账簿没有改动」。

- **一个上海日历日一次复核。** 一次复核属于它的 `as_of` 落在的上海日历日。第一次写 `RT/daily_survivor/<cfg>/<交易日>.morning.json`。在**更晚的日历日**再跑（仍在下一交易日 09:15 之前，例如周五晚间、周六做过一次、周一 08:30 再做），会重新复核：新的钉住、一次请求、一个新文件 `<交易日>.morning.<YYYY-MM-DD>.json`（日期是这次复核的上海日期），之前的文件原样保留，从不拿来顶替这一次——周六的「没有变化」看不见周日才发布、日期是周五的 ST 公告，周一的复核看得见。**同一个日历日**再跑：已完成的文件重印，0 请求、0 写入；钉住之后中断的，用钉住的 `as_of` 和文件里存的晚间读取继续。在比已有复核**更早的日历日**复核（例如 `--as-of` 拨回去）：第 2 步拒绝，`a check is never filed under an earlier date than one already made`，什么都不取、不写。
- **后来的复核不在当晚的时钟上重读库。** 第一次复核取数之后，当年的 `namechange` 分区已被重述，在当晚的时钟上读库已经读不出当晚看到的样子。所以更晚日历日的复核沿用前一次复核在**它自己取数之前**存下的晚间读取，文件键 `carried_from` 写明出自哪个文件、哪个时刻（第一次是 `null`）；这份读取照样与当晚的文档核对，不符就点名它出自的文件拒绝。代价是：「库被清晨取数以外的东西改过」这道防线只有第一次复核有。
- **打印的样子**：第一行 `morning re-check   the plan of <交易日>, read again on <日期> (<上海时刻>), before the next session's call auction -- advice only: …`；后来的复核多一行 `earlier check      read on <日期> (<时刻>), <文件名>, kept as it is: …`；然后是 `holdings compared`、`advice`、（变了的话）`counts`、（有的话）`tolerated`、`notices`、`tushare requests`、`wording`。计划按交易日称呼（`the plan of <交易日>`）：早上 08:30 时，「今晚的计划」已不是哪一晚的计划。
- **看得见的**：公告日期不晚于那个交易日的更名，主要是公告日期就是当天、却在晚间读取之后才发布的 ST 或退市风险更名。建议一栏是 `no change to the plan of <交易日> among announcements dated through <交易日>` 或 `<n> difference(s) from the plan of <交易日> among announcements dated through <交易日>`，之后逐条：`do not place BUY <代码>: <原因>`（顺延的买单后面加 `(a buy carried from an earlier session)`）；`holding <代码> turned <原因>: the paper book sells it at the next evening`（只是停牌时是 `the paper book freezes it at the next evening (it cannot trade while suspended; it is not sold)`）；`holding <代码> left the survivors (still eligible): the paper book sells it at the next evening, unless that evening's replacement cap defers it`；`watch list changed: …`。合格数、幸存者数、名称语料的 ST 与退市计数变了的，单独一行 `counts`（`<计数> <晚间> -> <清晨>`，后面说明 `information, not advice`），**不算一条差异**：计划之外的一个名字变成 ST，只动这些计数，不要求你做任何事。在登记簿上市行之前就有日线的代码列在 `tolerated` 下，不算建议。
- **看不见的**：公告日期晚于那个交易日的更名（开盘前、周末或假期里发布的）。库里（取数之后）计划里的名字的这类更名列在 `notices` 一行（`announced after <交易日>, not screened -- a notice, not advice: …`）下，每条 `<代码> <名称> <公告日> <变化>`：通知不要求做任何事，下一晚会筛它。新年时清晨只问那个交易日所在的一年，所以公告日期在新一年的更名既不筛、也不通知。**「no change」从不证明没有 ST 公告。**
- 文件里的 `held` 是当晚钉住的持仓（当晚成交与结算之前的账簿；第一晚是 `[]`，虽然那晚的买单成交后就有持仓）；建议所说的持仓是结算之后的账簿，文件键 `holdings_compared`，打印为 `holdings compared`。
- **重跑**：同一个日历日的已完成文件只在 09:15 之前重印，0 请求、0 写入（截止时刻在重印之前就查）；钉住之后中断的，用钉住的 `as_of` 和文件里存的晚间读取继续。
- **退出 1**（每条都写明是第几步，并打印已花的请求；步骤是 registration、preconditions、panel update、facts、summary）：时钟或（钉住的）`--as-of` 已到 09:15；`--as-of` 不晚于当晚自己钉住的时钟；比已有的复核更早的日历日；那个交易日没有晚间日志（信息说先跑晚间：`Run the evening first -- the same command without --morning-recheck -- before 09:15 of the next session, to plan its open`）或日志没写完；那天是纪元日或只结算日（没有计划）；清晨文件是另一晚或另一登记的，或是手改过的已完成文件，或名字里的日期与它的 `as_of` 不符（原样保留）；纸面账簿的写锁被占用；漂移——库里（或沿用的那份晚间读取里）已经给不出当晚的事实，或某个计划买入、顺延买入、观察名单上的名字在重读里不再是幸存者（这种情况什么都不取）。
- **退出 2，0 次请求**：P6 登记（P6 没有清晨计划）；`--full-update`、`--top`、`--dataset`。与 `--factor-gaps`、`--pin-worktree`、`--launchd-plist`、`--launchd-morning-plist` 同用是 argparse 的退出 2。
- 给 `V2-P7-006`：清晨取数之后，当年的 `namechange` 分区被重述，一条当天发布晚了的 ST 行在当晚自己的时钟上也看得见了，晚到记录核查于是把那一晚如实登记的记录判为 `unverifiable / recompute_differs / namechange:<年> (its rows through <交易日> were restated)`。不跑清晨复核，下一晚自己的面板更新给出同样的结论。所以每一条当天发布晚了的 ST 公告都会让那一天的记录变成 UNVERIFIABLE，协议要报告它们的占比。

### 重跑与补救

- 日志已有 `result`：再打印一次，0 请求、0 写入（已过集合竞价的计划在 ORDERS 下加那一行）。
- 日志没写完：按钉住的 `as_of` 与 `held` 从停下的地方继续——`panel` 已记录就跳过第 2 步，第 4 步跳过已建的时点，记录复用；每次运行在发请求之前都核对账簿仍是钉住的那本。
- 被拒的一天不写 `result`：修好之后重跑，就会跑它的晚间（如果还在 09:15 之前）。
- **永远不要删除已提交那一天的日志。** 丢了的话，从与纸面账簿目录一起做的备份恢复。没有备份：在下一交易日 09:15 之前照常再跑这一天，它重新推导已提交的晚间，纸面账簿一字不写；09:15 或之后再跑，会在第 5 步（paper head）被拒，信息里点名丢失的日志并给出 `--as-of <交易日>T18:30:00+08:00`：用这个 `--as-of` 重跑，这一天又是晚间，它找到已提交的交易日、重新推导、不写账簿，并打印集合竞价已过。这个补救要在下一交易日的晚间运行之前做。
- **前一晚已提交、日志没写完**（那次运行在快照与摘要之间停下）：下一个交易日的运行在钉住之前、任何请求之前，在第 5 步拒绝：`rerun <D> first: its evening is committed but its journal is incomplete …`，下一行是重跑 D 的完整命令——`UV_PROJECT_ENVIRONMENT="$PWD/.venv" uv run --no-sync --env-file .env "$PWD/.venv/bin/python" scripts/daily_selection.py --runtime-dir <RT> --registration <登记> --repo <检出> --as-of <D 钉住的时刻，上海时间>`——再一行 `then rerun this command`。照做：D 的重跑按它自己钉住的时钟仍是晚间，找到已提交的交易日，重新推导、纸面账簿一字不写，把日志补完（过了集合竞价，计划下面会多那一行）；然后再跑原来的命令。之所以拒绝而不是越过：一旦更晚的交易日把账簿推过 D，D 的计划、订单和决定就再也写不进任何文档。（D 的快照若既没有留下任何单、首次决定又在更早的交易日——这与补结算留下的快照分不开——只有 D 与这一天之间没有别的交易日日志时才这样拒绝。）这次拒绝也打印上面「被拒的一天对账户意味着什么」那一段。
- **登记换了，就是另一本账。** 纸面账簿的标记绑定登记文件的 `registration_sha256`。上线之后改了受绑定路径下的代码（要重新登记）或改了登记的 `settings`，登记文件的 sha256 就变了：第 5 步在任何请求之前拒绝，信息点名两份登记的 sha256。新登记要在**新的运行目录**里、用**新的纪元**（新登记第一次计划运行的前一个交易日）开一本新账；旧目录的账簿仍属于旧登记，不要把新登记指向它。一次修复能不能让账簿跨登记延续，由 `V2-P7-006` 决定；今天没有任何东西能做到。
- 第 9 步拒绝的日志（读不出、P6 日志、schema 不对）：照信息做——`move it aside -- keep it, it may be this day's own journal, damaged -- and run the day again`：挪开但保留，重跑会重新钉一份。
- 账簿与日志钉住的不符（纸面账簿目录被换过、移动过或恢复过）：第 5 步拒绝并给出补救——从同一份备份同时恢复快照与账本，或者把这一天的日志挪开后重跑，让这一天钉住现在的账簿。

### 重启：长时间停跑之后的第一次运行

每日登记自 2026-10-08 暂停，面板停在那时。**这条命令从不自己补一大段缺口**，重启要先手工补面板：

1. 第 2 步在发任何请求之前，数当年已存日历上面板落后当天多少个交易日：多于登记的 `max_panel_catch_up_sessions`（0 到 16），就拒绝，退出 1，一个请求都不发，打印补最老一批（至多上限那么多个交易日）的命令，形如 `UV_PROJECT_ENVIRONMENT="$PWD/.venv" uv run --no-sync --env-file .env "$PWD/.venv/bin/openalpha" panel build --runtime-dir RT --year <年> --as-of <这一批最后一个交易日>T16:30:00+08:00 --exchange SSE --incremental --dataset adj_factor --dataset price --dataset stk_limit`（「手动运行」的形式，在钉住的 worktree 里照抄；`--as-of` 是那天上海 16:30 的发布时刻）（会话级分区彼此不齐、其中一个已越过这一批时，打印的是不带 `--incremental` 的整年重建，并写明要取多少个交易日）。照样运行，再跑本命令：还多于上限就再拒绝一次、给出下一批；不多于上限，它自己补完。每个交易日约 5 次请求（`stk_limit` 分页时 7 次）。
2. 跨年时，上一年的会话级分区没到上一年最后一个交易日，第 2 步不论上限先拒绝，打印补齐上一年的 `panel build --incremental`（必须在新一年的第一次构建之前跑）；它不建 `trade_cal`，所以补完之后若当年日历还没存，会再拒绝一次，打印 `openalpha panel build … --dataset trade_cal`。
3. 因子档位错过的交易日超过 20 个时，第 4 步拒绝并给出分批的 `openalpha factor build` 命令（同 P6 的「错过的交易日」）。
4. 还没有纸面账簿时，纪元离第一次运行最多 `1 + max_panel_catch_up_sessions` 个交易日（否则第 1 步退出 2）：纪元登记为第一次计划运行的前一个交易日。

所以顺序是：用户确认 `V2-P7-006` 的登记；经用户同意，按上面的命令形状手工把面板补到最新已收盘交易日（数百次请求）；必要时补建因子档位；然后在纪元的下一个交易日收盘后、再下一个交易日 09:15 之前跑第一次。注意：第 2 步拒绝的那次运行已经把这一天的 `as_of` 钉进了日志（钉在任何请求之前），同一交易日的重跑沿用它。

### 已知局限（幸存者形态）

1. **新年第一个交易日之前没有更名公告：名称语料一侧已经处理（`V2-P7-021`，取值暂定），登记簿一侧也已处理（`V2-P7-025`）。** 当年第一条更名公告之前，Tushare 对当年的 `namechange` 一行也不给（2012 年第一条公告是 1 月 5 日，晚于第一个交易日 1 月 4 日）。以前面板拒写空分区，第 2 步在这个目标上失败，日志钉住了这一天的 `as_of`，每次重跑问的都是同一个空窗口，这一天丢了，不是推迟了。现在 `panel build` 把当年记成零行分区（输出里有一行 `EMPTY namechange year=…`），读名称语料的读者（事实、第 3 步 doctor、第 4 步因子构建、清晨复核的通知、迟到记录核查）只在到该年 1 月 31 日（含，上海日历日）为止把它读作「尚无更名」，当年第一条真实更名到来时零行分区被整份替换；失败或截断的抓取、过了窗口的空回答、已有更名行的年、不是当年的空回答仍按名拒绝；P6 的 `--full-update` 在一月初也不再因 `namechange` 失败，而是写空分区并继续。**「两种 `no_data` 都算经核实为空」与「到 1 月 31 日」是暂定取值，用户还没有确认**（常量 `NAME_YEAR_EMPTY_THROUGH`）。**登记簿的同一缺口已由 `V2-P7-025` 在本分支上关闭（未推送、未真实运行）**：整份登记簿抓取成功、观测年没有上市/退市时，`panel build` 把该生命周期年记成零行分区（输出里有一行 `EMPTY stock_basic year=…`），所有读者（`panel doctor` 检查 `stock_basic` 时、第 4 步因子构建、周报的标签读取、事实适配器，以及一切经 `load_stock_universe` 的读取）**只在到当年 12 月 31 日（含，上海日历日）为止**把它读作「今年还没有上市或退市」，当年第一条真实事件到来时零行分区被整份替换；失败或截断的抓取、`no_data` 的整份回答、过了窗口的空回答、已有行的年在相同或更晚的观测时刻仍按名拒绝；更早的重放什么都不写。此前这一年会丢：日志钉住了这天的 `as_of`，重跑会得到同一个 `partition_missing`（重跑是推断，未实测），前向周报的标签读取也被拒（P6 已知局限第 6 条记录了同一缺口，现由同一修法关闭）。

10. **账户与纸面账簿会分叉，而没有任何输入能把它们对上。** 纸面账簿假定每张打印的单都下了、都在开盘按开盘价成交（ORDERS 下面那一行就是这么说的）；没有「账户同步」的输入告诉它你实际下了什么、成交了什么（这是留给用户决定的产品选项，没有做；只读地列出账簿当前持仓的命令也没有）。你没下、没成交、照清晨复核没买，或者你的单成交了而账簿的被拒、过期了，从那天起两边就不同：账簿会为它持有、你没有的名字打印 SELL（照提示忽略），却永远不会为你持有、它没有的名字打印 SELL。每次分叉都记下来；纸面账簿的权益本来就不是证据。
11. **集合竞价限价单的说法是本系统的假设，要向你的券商确认。** 摘要说：集合竞价收限价单，买单挂涨停价、卖单挂跌停价就以唯一的开盘价成交；涨跌停价是从真实收盘价按主板 10%、ST（2025-07-07 之前）5% 算的，以交易所公布的为准。券商对集合竞价的委托价格、冻结资金与撤单的规则是否如此，没有核对过。
12. **买单只按 09:15 的现金定量，并按涨停价冻结。** 内核给今晚的买单定量用的是 **09:15 的现金**（纸面账簿结算后的数，是模型、不是账户真值），不是现金加今晚卖单的回款：卖单与买单在**同一个**集合竞价里，券商先冻结买单的钱，卖单的回款在竞价之后才到。每张买单按它的**涨停价**冻结（主板 1.10 倍、基准是信号日收盘、四舍五入到分）。350,000 元、10 只等权时十张涨停价买单要冻结约 38.5 万元、超过现金，最后一只只能买更小的股数（或整只不买），资金行下面按名字打印短少。集合竞价只收限价单、买涨停价 / 卖跌停价取单一开盘价、买单冻结约 1.1 倍名义，都是**本系统的假设**，没有向任何券商核对过（第 11 条）；下单前向你的券商确认，`FREEZE_RATIO` 待你向券商确认后改一个常量。真钱闸门仍然关闭：`006` 尚未经你确认并登记，账户成交对账输入也没有做（这次只做了现金约束的一半）。

15. 送股、拆分之后，positions 只给 `ledger/real ratio`（例如 `2.0000`），不给账户的股数，也没有「这是送股」的标记：现金分红也会动这个比值，从比值推不出是哪一种，所以不猜。卖出用 SELL ENTIRE POSITION 不受影响；要知道账户里有多少股，看你的账户。
16. 少数拒绝信息里的时刻仍按存的样子打印，可能是 UTC（`+00:00`，例如不带 `--as-of` 运行时钉住的时钟）：已提交的晚间丢了日志那一条（第 5 步）里的钉住时刻，以及清晨复核几条拒绝里的 `as_of` 与时钟。摘要、补救命令里的 `--as-of`、「被拒的一天对账户意味着什么」那一段都是上海时间。

> **状态与待定。** 本节写的是代码现在实际做什么（读自 `scripts/p7_smoke.py`、`scripts/p7_smoke_requests.py`、`scripts/p7_smoke_env.py`）；写本节时这套工具还没有对真实数据运行过，一次真实请求也没有发过，第一晚的情形由 `docs/research/p7-step0-validation/T10-real-data-smoke.md` 记录。下面写「待用户确认」的东西还没有定，本节不替用户定：阶段 1、阶段 2 的请求上限（路线图 `V2-P7-019` 行与 `docs/superpowers/plans/2026-11-01-p7-route-adjustment.md` 给的数字是估计，不是定下的上限；要按第一晚的日期由用户确认），以及谁来跑每一个晚上、阶段 2 手工跑还是另作安排。

### 为什么一律走 `scripts/p7_smoke.py`

1. **每日命令自己没有「到 100 就停」。** 最坏的一天会超过 100 次请求（见上文「每天取什么」）。驱动在已有的 `counted_transport`（`cli._panel_transport`，每日命令所有请求经过的那一个接缝）上挂一个到限即拒的计数器：越过上限的那一次请求不发出，也不会被重试。
2. **拒绝信息打印的补救命令，直接粘贴运行不受任何计数，而其中一种是整年重建（实盘规模约 1,200 次请求）。** 补救命令一律交给 `remedy`：它按命令自己的解析判断，认得出并拒绝整年重建、别的运行目录、别的登记。
3. **驱动固定运行目录、登记与钉住的 worktree。** 额外参数里出现这些路径选项（缩写和 `--选项=值` 的写法也算）一律拒绝，所以冒烟写不到 `~/openalpha-research`。它还拿一把根目录里的锁（一个根目录一次只有一个调用），给每个调用写账本记录和一份日志。

### 时间（多伦多）

多伦多自 2026-11-01 起是 EST（UTC−5），与北京差 13 小时；自 2027-03-14 起是 EDT，差 12 小时。

| 什么 | 北京时间 | 多伦多（EST） |
|---|---|---|
| 晚间 | 交易日 18:30 之后，次一交易日 09:15 之前 | 当天 05:30 之后、**当天 20:15 之前** |
| 第一晚 | 同上；预留 2 小时（因子补建，见下） | 05:30 开始 |
| 晨查 | 次一交易日 08:30–09:00 | 当天 19:30–20:00（在当天晚间之后） |
| 周五的晚间 | 截止周一 09:15 | 截止周日 20:15 |
| 周报 | 任意时刻 | 周六 |

- 运行时钟早于北京 16:30（多伦多 03:30）时，「当天」是上一个交易日。
- 截止是**下一个交易日**的 09:15（`registration_cutoff`）：遇节假日，截止顺延到假期之后的第一个交易日。
- 第一次运行就在截止之后，这一天是只结算日：不登记、不决定，摘要写 `NONE PLANNED tonight -- no evening was run`（见上文「一天是哪一种」）。这不是故障，但这一晚没有记录，不能算进 G1。
- **重跑一个已完成的晚间，要看时区。** 从这一晚跑完，到北京时间次日 16:30（多伦多次日 03:30）之前，`smoke evening` 重印该晚（0 次请求；北京次日 09:15 之后，ORDERS 下多一行「集合竞价已过」）。多伦多次日 10:00 已是北京 23:00：次日 16:30 的发布早已过去，次日若是交易日，`smoke evening` 开出的是**新的一晚**（约 16–22 次请求），不是重印——这要先问用户，不能当作重跑随手做。
- 晨查和周报不要与晚间同时跑；驱动的锁会拒绝第二个调用（`another smoke invocation holds …`）。

### 准备（一次，0 次请求）

在主检出里做，站在含冒烟横幅与冒烟三个脚本（`scripts/p7_smoke.py`、`scripts/p7_smoke_requests.py`、`scripts/p7_smoke_env.py`）的 `main` 提交上。`prepare` 要求被克隆的提交就是这个检出的 `HEAD`、是 `refs/heads/main` 的祖先，且受绑定路径与这三个脚本相对 `HEAD` 没有未提交的改动；主检出里要有 `.env`（`prepare` 只查它在不在，从不打开它）。

**动手前先看这几件事，都不花请求：**

1. **主检出是不是浅克隆**：`git rev-parse --is-shallow-repository`。本仓库的主检出 2026-11-02 打印的是 `true`。浅克隆上 `git clone --local` 退回传输克隆，「提交在 `main` 上」的检查读的是被截断的历史，可能判错；`prepare` 只为此打印一行警告（`smoke: warning: … is a shallow repository …`），然后照常继续，不会因此拒绝。所以这一条要在 `prepare` 之前由人看：打印 `true` 时先问用户怎么处理。
2. **面板的卷**：源面板（`~/openalpha-research/panel`，约 6 GB）与根目录的父目录必须在同一个卷上，否则 `prepare` 拒绝；同卷还不够——只有 APFS 上 `cp -c` 才是克隆，同卷但不支持克隆的文件系统（HFS+、exFAT）上它退回真复制，整份面板都会被拷。先用 `diskutil info` 看 `File System Personality`。`cp` 在 `PATH` 上只查一次，必须解析到 `/bin/cp` 或 `/usr/bin/cp`；排在前面的 GNU `cp` 把 `-c` 读成 `--preserve=context`，会拷整份，`prepare` 拒绝——但这一条到第 8 步才查，那时根目录已经建了，要由用户删掉再来，所以先看 `which -a cp`。
3. **根目录的位置**：解析后的路径不含空白（uv 按空白拆 `--env-file`）；不在任何临时目录里（`/tmp`、`/private/tmp`、`/var/folders`、`tempfile.gettempdir()`；冒烟要跑几周，系统会清它们）；不在主检出里、不在 `~/openalpha-research` 里（不分大小写，按路径名和文件身份都比）、不在它所克隆的检出或面板里；它不能已经存在，它的父目录必须存在。根目录建好后不要挪动或改名：`smoke.json` 记着建时的路径，读到不符就拒绝（钉住的 worktree 与克隆靠建时的路径互相链接）。
4. **「前」的快照**（G8 要拿它对照「后」）：

```bash
git rev-parse --is-shallow-repository
git log -1 --format=%H
git status --porcelain=v1 --untracked-files=all
git status --porcelain -- src scripts pyproject.toml uv.lock
ls -la ~/openalpha-research
shasum -a 256 ~/openalpha-research/panel/catalog.duckdb docs/research/p6-registration.json
ls ~/Library/LaunchAgents | grep -i openalpha
pgrep -fl openalpha
which -a cp
```

第四行（受绑定路径，加上 `scripts/` 的其余部分——预检比 `prepare` 的要求略严）必须没有输出；第七、八行也应没有输出（没有 launchd 配置、没有别的进程在写面板）；`which -a cp` 的第一行必须是 `/bin/cp` 或 `/usr/bin/cp`。`prepare` 之后它打印的 `catalog sha256` 应与第六行里 `catalog.duckdb` 的 SHA-256 一致。

**然后**：

```bash
mkdir -p ~/openalpha-smoke
uv run --no-sync python scripts/p7_smoke.py prepare --smoke-root ~/openalpha-smoke/r1 \
  --epoch <第一晚的前一个交易日> --phase1-cap <待用户确认> --phase2-cap <待用户确认>
```

- `--epoch` 是第一晚的**前一个**交易日，必须是已存日历里的开市日。`prepare` 不查日历，纪元选错要到第一晚的第 1 步才被拒绝（退出 2）；它写进冒烟登记就不能挪：还没有账簿时，纪元到当天最多相隔 `1 + max_panel_catch_up_sessions`（设计值 10，即 11）个交易日，第一晚拖过这个距离也只能用新纪元 `prepare` 一个新根目录。越晚开始，补抓越贵。
- 两个上限都是整数请求数，阶段 2 的（**整个冒烟的累计**，含阶段 1）不小于阶段 1 的。数值待用户确认；定的时候要留起步额度：当前阶段的上限减去已花，至少还剩 22 次才能起一个 `evening`，至少还剩 `7 ×（max_panel_catch_up_sessions + 1）`（设计值 77）次才能起一个 `panel build` 补救，不够就在调用前被拒绝（退出 5）。
- `--commit` 缺省是这个检出的 `HEAD`（也只能是它）；`--source-panel` 缺省是 `~/openalpha-research/panel`，不是仓库自己的 `runtime/panel`（那是另一份、小得多的面板，`prepare` 拒绝）；`--uv` 缺省是 `PATH` 上的 `uv`。

**它做的十步，按这个顺序。第 1–5 步的拒绝什么都不建；从第 6 步起根目录已经存在、只含这次 `prepare` 做的东西，拒绝信息点名它，由用户删除——`prepare` 从不删除任何东西。**

1. 根目录：上面第 3 点的全部规则。
2. 来源：主检出有 `.env`；源面板有 `catalog.duckdb`；两个上限合规。
3. 提交：完整的 40 位 id，是 `HEAD`、在 `main` 的历史上，受绑定路径干净。
4. 同一个卷（上面第 2 点）。
5. 配置能被每日命令的第 1 步读通（带登记的随机种子）。
6. `git clone --local --no-checkout` 到 `<根>/repo`，**随即删掉 `origin`**（克隆保留的 `origin` 指回主检出，一次手滑的 `git push` 会把冒烟登记送进去），再在提交上建分支 `v2-p7-019-smoke`。
7. 在克隆里写冒烟登记（`docs/research/smoke/v2-p7-019-smoke-registration.json`；设计的书与 adapter、占位的 `survivor_forward_protocol`、`settings` 里的 `smoke_run` 标记），只在克隆里提交，用固定身份，无 hook、无签名。
8. `cp -c -R` 克隆面板到 `<根>/runtime/panel`：克隆前后源面板的文件、大小、修改时间必须相同（否则它在被克隆时变了），副本的文件与大小与源一致，`catalog.duckdb` 逐字节一致；记下它的 SHA-256。
9. 钉住的 worktree `<根>/pinned`（每日命令自己的 `--pin-worktree` 那几步：钉在登记的提交上、离线建 `.venv`），其中 `.env` 链到**主检出的** `.env`（对一次性克隆跑 `--pin-worktree --repo <克隆>` 会链到克隆里不存在的 `.env`，晚间就没有凭据）。uv 缓存缺包时离线建环境失败，信息给出一条联网补缓存的命令——那是联网（不是 Tushare），先问用户；补完后由用户删掉这个半成的根目录再 `prepare`。
10. `<根>/smoke.json`（只写一次）与请求账本 `<根>/requests.jsonl` 的第一条 `prepared`。

**之后**，每次调用都在钉住的 worktree 里经驱动做。定义一个 shell 函数（`prepare` 也会把它按这个根目录打印出来，以它打印的为准）：

```bash
smoke() { ( cd ~/openalpha-smoke/r1/pinned && UV_PROJECT_ENVIRONMENT="$PWD/.venv" \
  uv run --no-sync --env-file .env "$PWD/.venv/bin/python" scripts/p7_smoke.py "$@" ) }
```

**准备之后核对**：

- `smoke status`：已花 0（`spent         0 of <阶段 1 上限> (…remain)`），`phase 1`，没有 `unclosed`、`discarded     no`。
- `git -C ~/openalpha-smoke/r1/repo remote` 没有输出。
- `ls -l ~/openalpha-smoke/r1/pinned/.env` 是指向主检出 `.env` 的符号链接。
- `cat ~/openalpha-smoke/r1/pinned/.venv/pyvenv.cfg` 的版本是 3.11.x。

### 驱动的子命令、退出码与输出

| 子命令 | 在哪里跑 | 做什么 | 请求规则 |
|---|---|---|---|
| `prepare …` | 主检出 | 上面的十步 | 0 次请求 |
| `evening [-- 选项]` | 钉住的 worktree | 每日命令 `scripts/daily_selection.py` | 起步要求还剩 22 次；没有单次上限（只受剩余额度限制）；撞上限丢弃根目录 |
| `morning [-- 选项]` | 同上 | 同一命令加 `--morning-recheck` | 单次至多 3 次，起步要求还剩 1 次；撞上限不丢弃根目录 |
| `weekly [-- 选项]` | 同上 | 前向周报 `scripts/forward_report.py`（不是每日命令） | 单次上限 0：任何请求都被拒绝；不丢弃根目录 |
| `remedy 行`、`remedy -` | 同上 | 运行一次拒绝打印的那一行（`-` 从标准输入读） | 按补救的种类：`panel build` 起步要求还剩 `7 ×（max_panel_catch_up_sessions + 1）` 次，没有单次上限，撞上限丢弃根目录；`factor build` 上限 0，不丢弃；每日命令形式的补救（`rerun <D> first`）按 `evening` 或 `morning` |
| `status` | 钉住的 worktree（经 `smoke`）；从别处（例如主检出）要给 `--smoke-root <根>` | 阶段、两个上限、已花、是否丢弃、未关闭的调用、逐次调用、按接口的合计 | 无 |
| `phase --to 2 --reason "…"` | 同 `status`：经 `smoke`，或从别处加 `--smoke-root <根>` | 阶段 1 进阶段 2，只能做一次 | 无 |

`evening`、`morning`、`weekly` 的 `--` 之后是该命令自己的选项（例如 `smoke evening -- --json`；不写 `--` 的 `smoke evening --json` 是驱动的用法错误，退出 2）；`--runtime-dir`、`--registration`、`--repo`、`--morning-recheck`、`--pin-worktree`、`--launchd-plist`、`--launchd-morning-plist`、`--factor-gaps` 是驱动的，不能给。

**退出码。**

| 码 | 意思 |
|---|---|
| 0 | 被包住的命令退出 0；`prepare`、`phase` 完成；`status` 的账本完整 |
| 1 | 被包住的命令自己的 1，原样透传：每日命令的 `step N (名称) failed`、周报的拒绝、`panel build` 自己判定面板不健康（`unhealthy`） |
| 2 | 用法：驱动自己的参数错误（argparse），或被包住的每日命令/周报自己的 2（例如第 1 步拒绝的 `--full-update`、`--top`、不够的 `--dataset`）。后一种调用已经开始，账本里有它 |
| 3 | **没有任何东西运行**：每日命令自己的 3（第 1 步准入拒绝：代码或登记不对、登记自相矛盾，都在纸面账簿、日志和任何请求之前），或驱动发现 `openalpha` 不是钉住 worktree 的那一份（`ForeignPackageError`）。被包住的 `panel build`/`factor build` 自己的 3 一律改成 7，所以驱动给出的 3 永远表示什么都没运行 |
| 4 | **请求上限，且只有上限**：越过上限的那一次请求没有发出。收尾行写 `exited 4 (the command's own N)`，N 是命令对那次被拒请求的反应：每日命令的 1（第 2 步拒绝），`panel build` 补救的 5（它把上限异常报成 `internal_error`）；异常一路穿出命令时没有这一行，只有 `REQUEST CAP REACHED` 那几行。被包住的 `panel build`/`factor build` 自己的 4/5/6 不会在这里出现，它们是 7（`exited 7`，没有碰上上限） |
| 5 | 驱动自己的拒绝：`smoke: refused: …`——账本或 `smoke.json` 读不通或不完整、额度不够起步、补救命令被拒、根目录已丢弃或有未关闭的调用、`prepare` 的各种拒绝；账本被拒时 `status` 也退出 5 |
| 7 | 被包住的 `panel build` 或 `factor build` 以它自己的 3、4、5 或 6 失败（`PanelExit` 的 `bad_request`、`provider_failure`、`internal_error`、`catalog_busy`）。结尾那一行写出它自己的码：`exited 7 (the command's own N)` |
| 130 | 中断（Ctrl-C、关闭终端、SIGTERM） |

**驱动打印什么。** 调用开始：`smoke <种类>: phase P, X of CAP requests spent (R remain)`；结束：`smoke <种类>: invocation N exited C; K request(s) sent {"接口": 次数, …}; phase P: X of CAP requests spent (R remain)`（都在标准错误，只在终端，不进日志）。被包住命令自己的标准输出和标准错误**原样**写进 `<根>/logs/<序号>-<种类>.out` 与 `.err`（排他创建，从不覆盖；种类是 `evening`、`morning`、`weekly`、`panel-build`、`factor-build`），同时打印到终端。`<根>/requests.jsonl` 是只追加的请求账本（`prepared`、`phase`、`start`、`end`、`discarded`），已花请求数是各 `end` 的 `count` 之和；驱动数的是真正发出去的请求。

### 第一晚

每一步之前先对用户说明范围与预计请求数，得到明确同意。

1. `smoke evening` → 预期第 2 步拒绝、0 次请求（面板停在 2026-10-08 附近，落后超过设计的 `max_panel_catch_up_sessions`；那一年的日历没存时，先花 1 次 `trade_cal`），打印最老一批的 `panel build`。

3. 回到 1，直到第 2 步不再拒绝；晚间自己取剩下的会话。
4. 第 4 步：若 P6 最后一次因子构建（10-08，这是从配置和 10-08 的日志**推断**的，没有读目录库）到当天超过 20 个会话，拒绝并打印 `openalpha factor build` 的分批命令——同样 `pbpaste | smoke remedy -`（0 次请求，本机 CPU；T6 在 2020 年的面板副本上测得年末一个会话的四个因子约 4 分钟，这里只是量级；20 个会话要一个多小时）。
5. 第 5 步在纪元开账；第 6–9 步照常；摘要首尾是横幅；`smoke status` 记下累计。
6. 立刻再跑一次 `smoke evening`：0 次请求、`the day was already complete`（幂等）。「立刻」指这一晚跑完之后、多伦多次日 03:30（北京次日 16:30）之前；再晚，次日若是交易日，开出的就是新的一晚，见上文「时间」里「重跑一个已完成的晚间」那一条。

`smoke evening`；在第 3 个晚上**故意不跑**（第 4 个晚上的摘要应有 catch-up 一行补结算它、不做决定）；第 2 个晚上之后的多伦多 19:30 跑一次 `smoke morning`；周六跑一次 `smoke weekly`（预期：尚无成熟记录、没有 p 值、0 次请求；周报是 `forward_report.py`，不是每日命令，重跑 `smoke evening` 不是对它的检验）。每个晚上开始前都要再问一次用户：说明范围与预计请求数，得到明确同意，上一晚的同意不延续到这一晚。

### 每晚要记什么（写进 T10 的表）

列：北京交易日、多伦多开始/结束、子命令、退出码、拒绝的步骤与第一行、本次请求数/累计/上限、按接口、补抓的会话、因子补建的会话、ORDERS 的卖/买/顺延张数、unfunded/unaffordable、facts 的 universe/scored/coverage 与 `name_unknown_assumed_ordinary`、晨查的差异数、与脚本化市场的差异（`stk_limit` 分页、撤回复核 REFETCH、收益路径复现 BUDGET、停牌无日线、`namechange` 重述）、缺陷。**不抄任何收益数字、权益数字。**

- 请求数（本次/累计）：`smoke status` 逐次调用一行（`#序号 种类 开始时刻 耗时 exit 码 本次请求数`），驱动数的是发出去的；每日命令自己的 `tushare requests` 行在撞上限时多算那一次没发出的请求。`status` 打印的时刻是**北京时间**（多伦多时刻要自己减 13 小时），它的 `exit` 是被包住命令自己的码（调用以异常结束时写 `-`），不是驱动的退出码——被上限拦下的调用在这里可能写 1 或 5，驱动的退出码 4 要在调用后立刻记下 `$?`。
- 按接口：`status` 只给累计的 `by api` 一行；某一晚的按接口分列只在驱动的收尾行里（只在终端，不进日志，所以当场抄下来）和 `<根>/requests.jsonl` 里该次调用 `end` 事件的 `requests` 字段。
- 拒绝的步骤与第一行：标准错误里的 `step N (名称) failed: …`。
- 补抓的会话、因子补建的会话：摘要 diagnostics 下的 `panel catch-up`、`factor catch-up`。
- 与脚本化市场的差异：每日命令把 `panel build` 自己的输出留在内存里，成功的一晚不打印它；`BUDGET` 行存在当天日志（`RT/daily_survivor/<config_id 前 16 位>/<交易日>.json`）的 `panel` 块里，`REFETCH` 行不存，只能从按接口的请求数推断（推断就写明是推断）。经 `remedy` 跑的 `panel build` 会把全部输出（含 `BUDGET`、`REFETCH`）写进日志和终端。
- `RT` 是 `~/openalpha-smoke/r1/runtime`。

### 补救、上限与中断

**`remedy` 接受什么、拒绝什么。** 只接受拒绝信息打印的那一整行（恰好一行，从剪贴板来最稳），命令是形如 `"$PWD/.venv/bin/openalpha"` 的 `panel build`、`factor build`，或形如 `"$PWD/.venv/bin/python"` 后接 `scripts/daily_selection.py` 的每日命令（`rerun <D> first`）。驱动只认这个形状（一个以 `/.venv/bin/openalpha` 结尾的词，或这样的 `python` 后紧接那个脚本），不核对那条路径是不是这个根的钉住 worktree；补救在驱动自己的进程里运行，用的是这个钉住 worktree 的代码。拒绝时打印 `smoke: refused: …`，退出 5，什么都不写：

- 不是一行、读不成 shell 行、行里没有上面说的那种 `openalpha` 或 `python scripts/daily_selection.py`；
- 选项和值用 `=` 连在一起（`--runtime-dir=DIR`；拒绝信息把每个选项和它的值打印成两个词）；
- `openalpha` 的子命令不是 `panel build`、`factor build`，或请求了帮助（`--help`）；
- 按命令自己的读法，`--runtime-dir` 不是这个冒烟的运行目录（取最后一个；`~` 不展开）——冒烟从不在别的运行目录上建，尤其不在 `~/openalpha-research` 上；每日命令形式的补救则要求它的 `--runtime-dir`、`--registration` 就是这个冒烟的，给了 `--repo` 的话也必须是钉住的 worktree；
- **整年重建**：按命令自己的读法，`panel build` 既没有 `--incremental`，数据集又不是只有 `trade_cal`（`--as-of --incremental` 把 `--incremental` 读成 `--as-of` 的值，那就是没有 `--incremental`，同样被当作整年重建拒绝）。这样的补救会花约 1,200 次请求，而且面板副本此时处在只有丢弃才能修复的状态；
- 命令自己会当作用法错误拒绝的写法（例如不存在的选项 `--bogus`、不是整数的 `--year`）。这在每日命令那边会成为一次故障、丢弃根目录，所以在写任何东西之前先拒绝；
- 根目录已丢弃，或有未关闭的调用，或剩余额度不够这种补救起步（见上面的表）。

**上限。** 起步额度不够时，调用在写任何东西之前被拒绝（退出 5，`ask the user before the cap is raised`）。调用之中碰到上限：那一次请求不发出，调用结束，退出 4，标准错误打印 `REQUEST CAP REACHED  invocation N stopped: …`。

- `evening` 和 `panel build` 的补救会写面板，副本可能写了一半，所以**根目录被丢弃**（账本写 `discarded`）：之后这个根目录里的一切调用都被拒绝，永远如此。`morning`、`weekly`、`factor build` 的上限触发不丢弃，但仍要先问用户再做下一个调用。
- **不要在副本上补救，尤其不要照整年重建。** 先问用户；经同意后，从**原面板**、用**新纪元** `prepare` 一个新根目录（上限触发时打印的最后一行就是这条命令，带着指回原面板的 `--source-panel`）。
- 驱动没有改上限的选项：上限写在 `smoke.json` 里、只写一次，要换上限只能 `prepare` 新根目录。阶段 1 进阶段 2 用 `smoke phase --to 2 --reason "<用户的话与日期>"`，只做一次，已丢弃、有未关闭的调用、已在阶段 2 的根目录都拒绝。

**中断。** Ctrl-C、关掉终端（SIGHUP）、SIGTERM 都按中断收尾：账本写这次调用的 `end`，退出 130，打印一行以 `smoke: interrupted;` 开头的话，要求先跑 `status`。中断的是 `evening` 或 `panel build` 的补救（写面板的调用），同样**丢弃根目录**；`morning`、`weekly`、`factor build` 被中断只记 `end`。写面板的调用以任何一个没被命令自己接住的异常结束也同样丢弃根目录（`status` 里那一次调用显示 `fault <异常类名>`）；命令自己的拒绝（退出 1）不是故障，不丢弃。调用方自己忽略的信号（`nohup`、后台作业）保持忽略。被 SIGKILL 杀掉、断电的调用有 `start` 没有 `end`：`status` 显示 `unclosed`，账本拒绝之后的一切调用（退出 5），这个根目录就此作废。窄窄的一个窗口——中断落在 `start` 与调用之间，或 `discarded` 与 `end` 之间——也是同样的结果。被中断的 `prepare`（也是退出 130）可能只建了一半根目录：由用户删掉它再 `prepare`。

**账本被手工改过。** 驱动抓得到的：账本或 `smoke.json` 不见了、被清空、属于另一个根目录；账本被截到只剩 `prepared`，或被截掉最后几次调用而 `logs/` 里还有它们的日志；调用序号不是 1 到 N；某次 `start` 记的已花请求数与它之前各 `end` 之和不符；写面板的调用以上限或故障结束，却没有紧挨着 `end` 之前的那条 `discarded`；读不通的事件（按名拒绝这个根目录）。**抓不到的**（伪造，不是故障）：账本连同 `logs/` 一起被截；被改了字段的事件（例如最后一次调用的 `end` 的请求数；或者删掉 `discarded` 行再把那个 `end` 的 `fault` 改成空——一个已丢弃的根目录就能重新运行）；手工插入的 `phase` 行。账本防的是手滑和中断，不是有意篡改。

**修了受绑定代码就是另一份登记**：新根目录、新纪元，阶段 1 重做（见上文「重跑与补救」）。可以把**未被丢弃、且 `status` 没有 `unclosed`** 的旧根目录的 `runtime/panel` 作为新 `prepare` 的 `--source-panel`，省掉补抓的请求（被 SIGKILL 杀掉的调用只是 `unclosed`、不是 `discarded`，它的面板副本可能写了一半，不能当来源）。
